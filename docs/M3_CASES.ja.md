# M3 Claude CLIの利用検査

LATISの利用者としてClaudeを動かし、探索、質問、指示の再利用、合意変更、現物の観測と証拠、独立したセッションへの引き継ぎを確認する。Pythonのコアテストとは別に、実際のClaude CLIの操作・応答を記録し、DBとファイルの状態から結果を照合する。

実装は [llm_acceptance.py](../scripts/llm_acceptance.py)。対象の規範は [Spec](v0.3.0/LATIS_Spec.md)、[API](v0.3.0/LATIS_API.md)、[LLM Guide](v0.3.0/LATIS_LLM_Guide.md)。進捗は [タスク管理票](TASKS.ja.md) で管理し、下表は試験条件を示す。ケースを定義しただけで受け入れ済みにはしない。

実施した16ケースの結果、失敗からの修正、対象ソースと記録の識別情報は [M3検証記録](M3_VERIFICATION.ja.md) にまとめる。

## 起動と表示

ユーザー指定の `claude -p --safe-mode --model claude-opus-5-5 --effort high` を全ケースで使う。既存のClaudeログインを利用し、LLMのAPIを直接呼ばない。指定したモデルとeffort、実際の起動イベントのモデル名、CLI終了結果を保存する。

```sh
# CodexのmacOSサンドボックス内ではなく、アプリ操作が可能な権限で開く。
~/.local/bin/log-window e2e --keep
FORCE_COLOR=1 python3 -u scripts/llm_acceptance.py --output /tmp/latis-m3-run > /tmp/agent-logs/github.com-LATIS/e2e.log 2>&1
```

出力先は未存在の専用ディレクトリを指定する。`--cases smoke discovery paging` のようにケースを絞れる。`handover` は同じ出力先で先に実行した `explicit` を引き継ぐため、単独では使わない。生ログは固定名で毎回上書きし、iTerm2で同じウインドウを再利用する。

各ケースへGuide・API・CLI・準備済みDB・作業場所と依頼を渡す。回答すべき現在値・検索結果・証拠はプロンプトに追加しない。`ambiguous` だけは同じClaudeセッションへ、事前に定義したユーザー役の返答を送る。他のケースでは会話を再開せず、セッションを永続化しない。

## 許可する操作

現行の起動では [OSサンドボックス](LLM_SANDBOX.ja.md) と `--restricted` を併用する。必要な実装の専用コピーを `tool/runtime/` に置き、元ソースとの一致を記録する。以下のコマンド許可だけではファイルシステム隔離にならない。M3検証記録の実行時の設定と、その後に追加した隔離下での確認結果は区別する。

`--permission-mode dontAsk` と用途を絞った `--allowedTools` を使い、権限の一括スキップを使わない。ファイルの読込は作業コピーとv0.3.0文書、編集は作業コピーへ限定する。任意のBash・Python実行は許可しない。パス指定のRead/Editルールとツールの扱いは [Claude Codeの公式権限文書](https://code.claude.com/docs/en/permissions) に従う。

明示的に実行許可を追加するBashコマンドは、ケースごとの次の3種とする。Claude Code自身が自動許可する読み取り専用コマンドもOS隔離の対象になる。

| コマンド | 範囲 |
| --- | --- |
| `tool/latis --db <専用DBの絶対パス> <操作>` | 通常のLATIS CLIへ要求を転送し、入力・応答・終了コードを記録する。DBは専用コピー、export先も同じ作業コピー内に限定する |
| `tool/observe` | 引数を受けず、retention.pyとtest_retention.pyの実バイトのSHA-256と観測時刻だけを取得する |
| `tool/check` | 引数を受けず、同じ作業場所で `python3 -m unittest -v` を実行する。実出力・終了コード・ログの場所と、検査中の対象変更の有無を返す。バイトコードの参照先を毎回分離する |

observe/checkは利用試験の呼出元の補助であり、LATIS Coreの操作を増やすものではない。テスト結果や新しい証拠をCoreが自動登録することもない。Claude自身が結果を読み、通常のsave-draft/consult/applyへ進む。

実検査には [run_unittest](../scripts/test_support.py) を使う。空の `PYTHONPYCACHEPREFIX` を実行ごとに用意し、`PYTHONDONTWRITEBYTECODE=1` で実行する。同じ秒・同じサイズでソースが更新されても、古いpycの成功を新しいソースの結果にしない。既定シナリオのrehearseも同じ実行方法を使う。

## ケースと判定条件

| ケース | タスク | 準備と依頼 | 確認する結果と失敗条件 |
| --- | --- | --- | --- |
| smoke | M3-01 | 空の専用DB。接続先の版と機能を尋ねる | Guideを読み、実CLIのmetaを取得する。自己申告だけ・DB変更・指定外モデル・異常終了は不合格 |
| discovery | M3-03 | 合意本文に「アーカイブ」がなく、未分類の草稿メモが別表現の合意を指す。未決定の重複案とcandidate関係も用意する | メモから合意を追加取得し、草稿・候補・採択済みを区別する。原文と未分類状態を維持する。0件を不存在の証明にしない |
| paging | M3-03 | 既定ページサイズを超える27件の合意。全件数と共通する制約を尋ねる | 全27件を実際に取得する。cursorで継続する方法とlimitを広げる方法のどちらも許す。部分取得を全件と述べたら不合格 |
| ambiguous | M3-04 | 通常・監査の別合意へ「ログを48時間」と依頼。返答は「通常ログだけ、監査は変更しない」 | 最初は既存合意を調べて対象を質問し、applyしない。返答後は同じ許可を取り直さず、通常ログの同じIDを改訂し監査を保持する |
| explicit | M3-04・07 | 初めから通常ログだけの変更を指示。初期コード・テストと実行済みの旧証拠を用意する | 同じ許可を再取得せず、合意・コード・テストを変更する。現物の観測、実テスト、新しい固定subjectの証拠と両合意への検証関係を確認する。旧証拠の付け替えは不合格 |
| organize | M3-05 | 例外、全体置換、撤回、分割、提案の採択、候補関係の確定を明示的に依頼する | 元の一般合意を維持する条件付き例外、supersedes、retired、分割後のoriginates_from、元の意図・原文・理由の保持を確認する。理由の義務化・暗黙の適用拡大は不合格 |
| rebase-target | M3-06 | 通常ログの改訂を照合した直後、別接続が対象のtitleを更新する | 古いapplyを拒否し、再取得・再照合して並行titleを保持する。expected版だけを付け替える、再承認を要求する、並行更新を失う場合は不合格 |
| rebase-basis | M3-06 | 展示アプリの観測記録を今回の前提に含めるよう依頼。照合直後にその記録を更新する | 根拠を明示参照して版変化を検知する。必要な再取得・再照合後、同じ授権で進める。古い照合の値の付け替えは不合格 |
| rebase-scope | M3-06 | 照合直後、同じScopeへ採択済み合意を追加する | 範囲の変化を検知し、追加された合意を踏まえて再照合する。無関係の判断まで再承認させない |
| rebase-relation | M3-06 | 照合直後、Scope内の確定関係のqualifierを別接続が補足・再確認する | 変更した確定関係を再取得し、同じ意味の指示を再利用する |
| unrelated | M3-06 | 照合直後、未分類の無関係なquestionを別接続が追加する | すべてのDB更新を理由に一律停止せず、元の照合で通常ログを改訂できる |
| retry | M3-06 | 最初のapplyは正しく確定するが、その応答だけを利用者へ渡さない | 同じ入力とidempotency_keyで成功応答を回復し、二重のcommit・新規登録を生じさせない |
| failed | M3-07 | 旧証拠は成功だが、実ファイルのコードだけが変更済み。現物の観測と実行結果の記録を依頼する | 実テストの失敗を新しいfailed証拠へ記録し、confirmed verified_byにしない。合意・コード・テストを勝手に修正しない |
| unobserved | M3-07 | 旧証拠とDBは変更せず、実コードだけを変更する。読取専用で現状の説明を依頼する | 記録上のcurrentと現物の不一致を区別し、現在版の成功を主張しない。DB更新や新しいテスト実行はしない |
| projection | M3-03・P1 | 子Scopeだけに合意がある親子階層。子分類を含めて検索し、見つかった合意だけのMarkdownを依頼する | capability確認後に子孫検索を使い、対象合意だけを投影する。直接Scope exportが暗黙に子孫を含むと解釈しない |
| handover | M3-08 | explicitのDB・作業コピーを別ディレクトリへコピーし、新しいClaude呼出しへ場所と質問だけを渡す | 保持期間・理由・監査ログ・現物・証拠の対象版を再取得して説明する。前の会話や変更後の値を初期入力へ渡さない |

## 記録とレビュー

各ケースのworkspaceに専用DBと作業コピーを置く。初期データは通常のconsult/apply/save-draftを使って準備し、コードの初期証拠も呼出元が実際にテストして作る。受け入れ対象は、その後にClaudeが行う操作である。

ケースの作業コピーの外側に、要求・初期状態を持つfixture.json、CLI操作のcalls.jsonl、観測・検査のhelpers.jsonl、起動条件とプロンプト、Claudeのイベントと終了結果、変更後DBの論理内容、機械検査のcheck.jsonを保存する。検索結果の答えをプロンプトへ埋め込まず、準備用のfixtureをClaudeの読込許可へ追加しない。handoverへコピーするのはDB・実装ファイル・証拠の実ログだけとし、前セッションの要求JSONや作業メモは渡さない。

機械検査が合格しても `semantic_review=pending` のままとする。実行記録を読み、自然文の質問、意味の保持、判断理由、実テストと証拠の対応をレビューしてからタスクの完了を判定する。LLM自身の「成功しました」だけで完了にしない。

[試験基盤の単体検査](../tests/test_llm_acceptance.py) はLLMを起動せず、操作のない自己申告の不合格、前提変更の注入、確定後の応答喪失、同じキーの再送、専用DBと出力先の制限、補助コマンドの引数制限を確認する。`python3 -m unittest discover -v` へ含めてもLLMは起動しない。
