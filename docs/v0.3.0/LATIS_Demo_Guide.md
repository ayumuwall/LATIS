# LATIS Demo Guide

- 版: `v0.3-demo-draft.1`
- 作成日: 2026-11-04（日本時間）
- 対象日: 2026-11-07（日本時間）
- 状態: 展示の実装・準備・確認手順。LATIS 本体の完成や性能達成を示す報告ではない。

## 1. 展示で伝えること

人間が通常の言葉で依頼すると、LLM が必要な合意を探し、未解決の判断だけ確認して、変更の理由と検証結果を次のセッションへ残せることを示す。
主役は、検索、採択前の照合、判断の再利用である。来場者に CLI、Scope、関係の種類を選ばせない。

一つの流れを最後まで成立させる。

1. 通常ログと監査ログの合意を見つける。
2. 曖昧な変更指示についてだけ対象を打診する。
3. 通常ログの保持を 24 時間から 48 時間へ改訂し、理由と履歴を残す。
4. 実コード・テストを観測し、実際のテスト結果を新しい証拠として結ぶ。
5. 別セッションの LLM が、その判断・理由・確認した版を使う。

この版は小さな代表データで実演する。20 万合意の性能測定、複数組織の認証・同意管理、分散同期を達成済みと説明しない。
LATIS Core は外部 AI サービスを内蔵する必要がない。利用する LLM がネットワークを必要とする場合、その条件は別に表示する。

## 2. 展示用の題材

以下は、すべて架空の展示設定である。法令や一般的なログ保存期間の推奨ではない。

| 対象 | 初期状態 | 変更後 |
| --- | --- | --- |
| 通常ログの合意 | 24 時間保持 | 48 時間保持 |
| 監査ログの合意 | 90 日、すなわち 2160 時間保持 | 90 日を維持 |
| 通常ログ変更の理由 | 障害調査の時間を確保したいという要求 | 採択時の判断理由と出所へ残す |

通常ログと監査ログは別々の agreement とする。主実演では、通常ログの同じ ID の本文を改訂し、旧版へ `history` で戻れるようにする。
監査ログへ適用される例外や暗黙の上書きを作らない。全体置換と `supersedes` は追加の受け入れケースで検証する。

同梱する題材は `examples/demo_project/retention.py` と `test_retention.py` である。
初期の `retention_hours(log_kind)` は `normal=24`、`audit=2160` を返し、テストもその値を確認する。
採択後、エージェントが通常ログの実装と期待値を 48 へ更新する。監査ログの 2160 は維持する。

実行方法は、`examples/demo_project` を作業ディレクトリとして次のとおり。

```sh
python -m unittest -v
```

この fixture が動くことと、LATIS 本体が動くことは別である。展示前に両方を個別に確認する。

## 3. 必須構成と任意機能

必須なのは、JSON 入出力の CLI、SQLite の保存・復元、日常の 9 操作、LLM Guide、題材コード、実行ログを保存する場所である。
HTTP サーバー、MCP、専用 Graph UI、ベクトル検索を展示の前提にしない。
エージェントには開始時から [LATIS_LLM_Guide.md](LATIS_LLM_Guide.md) を読ませる。Guide の評価を最後の工程へ回さない。

| 機能 | 展示での扱い |
| --- | --- |
| `meta/search/detail/relation-detail/relations/history/save-draft/consult/apply` | 必須。構造化エラーを含め API 契約どおり動くことを確認する。 |
| `search_descendants` | P1。capabilities にあれば利用可能。なくても直接 Scope・全体検索で実演できる。 |
| `markdown_export` | P1。capabilities にあれば読み取り用の投影を出せる。なくても読み取り JSON と説明文で表示できる。 |
| `drift`、`verify`、Markdown import | 本版にはない。別コマンドを用意した体で説明しない。 |

任意機能がない場合の `UNSUPPORTED_FEATURE` は正しい応答である。黙って無視した結果を、その機能の成功として表示しない。
機能を削る必要があれば P1 と表示の装飾から削り、照合・原子的反映・証拠の対象版検査を省略しない。

## 4. 運営者による初期準備

ここだけは運営者の作業である。来場者への通常フローには含めない。

### 4.1 作業場所と接続先を固定する

1. 題材の 2 ファイルを実演用の作業ディレクトリへコピーし、元の fixture は残す。
2. 以後はその作業ディレクトリを基準にし、`file:retention.py` と `file:test_retention.py` の解釈を記録する。
3. 使用する LATIS 本体の版・起動方法、LLM の接続、DB パスを記録する。モデル名等は分かる範囲だけ記載する。
4. Guide への参照、DB パス、CLI 呼び出し方を既存のエージェント設定に入れる。会話の内容を丸ごと初期プロンプトに埋めない。

API 実装後の初期化例。以下の DB パスは実演用の作業ディレクトリからの相対パスである。

```sh
latis --db .latis/demo.sqlite init <<'JSON'
{"project_name":"ログ管理サービス"}
JSON
latis --db .latis/demo.sqlite meta <<'JSON'
{}
JSON
```

`spec_version=0.3-demo-draft.1`、`rules_version=core-0.3.1` と必須 capabilities を確認する。
通常操作で DB がなければ自動生成されるとは考えない。古い保存形式の自動移行も展示対象にしない。

### 4.2 初期データを正規の操作で作る

初期データはパッケージ内の `examples/seed_consult.request.json` を使い、まず `consult` へ渡す。
応答の `data.normalized_request` を展開し、返された `basis`、実演準備を根拠にする `decision`、新しい `idempotency_key` を加えて `apply` する。
`authority_ref` は展示用データを準備する実際の指示を指す。fixture の架空の ID や未実行の照合結果を、実 DB の結果に差し替えず使わない。
直接 SQL で accepted を注入したり、初期投入だけ照合・来歴を省略したりしない。

seed は Scope、通常ログ・監査ログの合意、理由、未整理の問い、コード・テストの `draft` artifact と基本関係を登録する。
エージェントは seed に含まれる初期ハッシュと、コピーしたコード・テストの現物が一致することを確認する。違いがあれば理由を調べ、観測結果を通常 artifact へ記録する。
未整理の問いを `kinds` と `lifecycles` を明示して探し、Scope なしでも検索できることを確認する。別の要求メモを残す場合も `save-draft` で行える。
初期の実テストを実行して、新しい evidence artifact と通常ログ・監査ログの `verified_by` を正規の手順で作る。
seed が登録した `implemented_by` も読み取りで確認する。各 ID・版・関係 ID は実際の応答から控える。

### 4.3 初期状態を退避する

初期合意、コード・テストの観測、成功した実行記録が揃ったら、一貫したバックアップを作る。
出力ファイルは新しいパスを使う。

```sh
latis --db .latis/demo.sqlite backup <<'JSON'
{"destination":"baseline.sqlite"}
JSON
latis --db .latis/demo.sqlite export <<'JSON'
{"format":"json","destination":"baseline.json"}
JSON
```

JSON の `format_version` は 3。復元用の正本はこの JSON または一貫した SQLite backup であり、Markdown 投影ではない。
初期コード・テスト、DB backup、採択・検証の応答、Guide、本体の版を同じ展示準備記録へ対応付ける。

## 5. 主実演の進行

### 5.1 普通の依頼から始める

来場者役は、LATIS の操作名を指定せず、次のように依頼する。

> 障害調査で前日のログが足りないので、ログを48時間残せるようにしてください。

LLM は「ログ」「保持」などの小さな問いで検索し、通常ログ 24 時間と監査ログ 90 日の本文を確認する。
必要なら理由、関係、未整理メモを追加取得する。決められた回数の検索を消化する必要はない。

この依頼だけでは変更対象が未確定なので、LLM は対象を絞った質問をする。

> 通常ログは24時間、監査ログは90日保持する合意があります。通常ログだけ48時間にして、監査ログの90日は維持しますか。

来場者役は「通常ログだけ変更し、監査ログは変更しない」と答える。
最初からその範囲を明示した依頼なら、この質問は省く。照合を通したこと自体を理由に承認を取り直さない。

### 5.2 合意を照合し、改訂する

LLM は通常ログ agreement の読んだ版を `expected_revision_id` に指定し、本文を 48 時間へ変える change_set を作る。
`consult` で対象と関連情報を照合し、監査ログを変えないことを確かめる。
対象や内容を変えた場合は、変更後の内容を再照合する。未解決の意味判断がなければ既存の指示を根拠に `apply` する。

ここで読み取り表示を一度更新する。

- 同じ通常ログ ID に、24 時間の旧版と 48 時間の現在版がある。
- 変更理由、実行者、指示の参照、照合した前提が履歴にある。
- 監査ログの本文は 90 日のままである。
- 合意が改訂された時点では、旧実行結果だけを根拠に新仕様を検証済みと表示しない。

### 5.3 コードを観測し、実テストを記録する

1. LLM が `retention.py` の通常ログを 48 に変更する。`test_retention.py` の通常ログの期待値も採択済みの要求に合わせ、監査ログの 2160 を確認する検査は維持する。
2. 両ファイルを実際に読み、正確なバイト列の SHA-256 を計算する。通常 artifact を `save-draft` で更新して、新しい版を得る。
3. 実演用の作業ディレクトリで `python -m unittest -v` を実行する。実出力と終了コードを保存する。
4. 新しい evidence artifact を作る。`subject_refs` にアプリ artifact とテスト artifact の実際の版を含め、確認した合意版も記録する。`method` にコマンドと作業ディレクトリ、`outcome` に実結果を入れる。
5. 成功していれば、新しい証拠への `verified_by` と必要な旧関係の終了を `consult` / `apply` で反映する。共用コード・テストを対象とした監査ログの検証関係も、新しい結果へ更新する。
6. `implemented_by` の根拠版が変わっている場合は、対応を確認してから再確認する。最後に読み取りで実際の関係・対象版・結果を表示する。

失敗・判定不能はその結果として残す。赤い結果を成功に書き換えず、修正後に実行した結果は別の evidence artifact にする。
実行前後に対象が変わった可能性があれば、同じ版を検証したと断定せず取り直す。
旧証拠の `evidence`、`locator`、`content_hash` は変更しない。旧結果を新コードへ `reconfirm` して、検証を済ませたことにしない。

### 5.4 別セッションで再利用する

新しいエージェントセッションを開始し、Guide、同じ DB・作業場所、通常のプロジェクト指示を渡す。
前の会話全文や「48時間に変えた」という答えを初期コンテキストへ入れない。
来場者役は次のように依頼する。

> 通常ログの保持期間と、その理由を確認してください。監査ログの扱いと、現在のコードを何で確認したかも教えてください。

LLM は必要に応じて検索・履歴・検証関係を読み、通常ログ 48 時間、変更理由、監査ログ 90 日、検証対象と結果を説明する。
「現在のコード」を説明する前に現物を観測し、記録した artifact の版が現物に対応するか確かめる。
記録と現物が一致し、判断も変わらなければ、同じ変更の承認を再取得しない。毎回全テストを再実行する儀式にもせず、既存の証拠が今回使える範囲を確認する。

## 6. 読み取り展示で見えるもの

専用 UI を新設しなくても、読み取り結果の表示と実行ログで、次の三列を並べられる。
生成した要約だけを表示せず、必要な原文・ID・版へ戻れる状態にする。

| 合意と判断 | 観測したコード | 実施した検証 |
| --- | --- | --- |
| 通常ログ 24→48 時間、監査ログ 90 日 | コード・テストの locator と artifact ID・版 | コマンド、作業ディレクトリ、実結果・終了コード |
| 現在の本文と旧版 | 内容ハッシュと観測ログへの参照 | evidence ID、対象版、実施時刻 |
| 変更理由・指示の参照 | `implemented_by` の参照版 | `verified_by` と旧結果への履歴 |

`accepted` と「検証結果がある」を分けて表示する。`basis_status=current` は記録された版が一致するという表示であり、Core が現在の外界を自動確認したという表示にしない。
実物が変わっていても、artifact へ未記録なら Core は変化を知れない。この限界と、LLM が現物を観測する役割を説明する。
検証関係がない・candidate・untracked・changed のものを緑の「確認済み」へ一括変換しない。

Markdown を使う場合は、`markdown_export` 対応を確認し、新しいディレクトリへ出力する。出力日時・参照した DB 版を添える。
`node_ids` と `scope_ids` の選択は同時指定しない。選択範囲外の参照先も ID が見えることを確かめる。
投影の編集で DB が更新されるように見せず、restore の入力にも使わない。

## 7. 実演のやり直しと結果の保存

各実演は専用の DB と作業コピーで行う。終了後は結果の読み取り・実行ログ・DB backup をその実演として保全する。
次回は元の 24 時間の fixture を新しい作業場所へコピーし、初期 backup を未存在の DB パスへ復元する。
次の例の `source` は、保管した backup の実際のパスに置き換える。相対パスはその時点の作業ディレクトリから解決される。

```sh
latis --db .latis/demo-next.sqlite restore <<'JSON'
{"format":"sqlite","source":"baseline.sqlite"}
JSON
```

既存 DB へ restore して履歴を上書きしない。新しいパスをエージェント設定へ反映し、`meta`、通常ログ 24 時間、監査ログ 90 日、現物の初期ハッシュを確認する。
前回の `basis`・cursor・変更リクエストを、復元後の新しい作業に持ち越さない。必要な問い合わせをやり直す。
題材コードだけ、または DB だけを初期化して整合した初期状態だと説明しない。

参照実装の `scripts/rehearse.py` で作った出力には、一組で戻す補助も使える。

```sh
python3 scripts/reset_demo.py --source /tmp/latis-demo-run --destination /tmp/latis-demo-next --state baseline --format sqlite
```

JSONから戻す場合は `--format json`、変更後の状態を再現する場合は `--state final` を使う。補助はソースリポジトリで実行する。コードと証拠ログのハッシュをDBの版と照合し、必要なファイルだけを未存在の出力先へ公開する。コードは実行せず、過去の証拠を新しい実行結果にしない。詳細はソースリポジトリの [実装ガイド](https://github.com/ayumuwall/LATIS/blob/main/docs/IMPLEMENTATION.ja.md#復旧と実演リセット) を参照する。

## 8. ライブと録画の切り替え

| 表示 | 条件 |
| --- | --- |
| ライブ | その場の依頼、LATIS の実応答、実行中のコードとテスト結果を表示する。 |
| 録画 | 成功したリハーサルの録画であること、記録日時、本体・題材の版を最初に表示する。 |
| 保存結果の説明 | 保存済み JSON、履歴、実行ログを読んで説明していると明示する。 |

リモート LLM やネットワークが使えない場合は、用意した録画または保存結果へ切り替える。
未実行の応答を補ってライブに見せたり、録画の成功結果を現在の実行結果として表示したりしない。
採択や保存の結果が不明なら、同一リクエスト・同一キーの再試行契約に従い、成功を確認してから進める。

11/6 の固定前に、少なくとも以下を確認する。

- 曖昧な依頼には対象だけを打診し、明示済みの依頼には同じ承認を求めない。
- 未整理メモが保存・検索でき、accepted と取り違えられない。
- 合意の改訂後も原文・旧版・理由が残り、監査ログの合意が変わらない。
- テスト対象のコードとテストの版を残し、旧証拠を新コードへ確認し直す操作が拒否される。
- 失敗・判定不能の結果が confirmed の `verified_by` にならない。
- 現物の未観測変更を Core が検知したと表示しない。
- 別セッションで必要な判断を再利用し、復元後の題材と DB が初期状態で対応する。
- 任意機能がなくても必須の流れを実演でき、ライブと録画を区別できる。
