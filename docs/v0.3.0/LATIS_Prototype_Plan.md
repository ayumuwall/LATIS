## 1. 展示で成立させる体験

LLMが必要時に過去の合意を検索し、未解決の選択だけユーザーへ確認し、決まった変更を正しく反映する。
さらに、実装とテストを観測して証拠を残し、会話履歴のない別セッションから合意・根拠・検証対象を再利用する。
11/4から小さな記録・検索を実際に使い、11/6までに一連の操作をリハーサルする。

導入前の全分類、重複解消、全関連合意の網羅、自然文の完全な自動判定を前提にしない。
すでに指示で決まった内容について、記録するためだけの承認を追加しない。
意味上の未整理を許容することと、構造不正や古い判断による書き込みを許容することを分ける。

## 2. 優先順位と実装環境

| 優先度 | 範囲 | 完了の扱い |
| --- | --- | --- |
| P0 | 正しい9操作、原子的更新、版・履歴・再照合・冪等性、LLM Guideによる利用 | 展示の必須条件。検査の省略で間に合わせない。 |
| P0 | 外部artifact、実際の検査結果、implemented_by／verified_by、根拠の対象版、退避・復元 | 展示の必須条件。実行していない検査を成功として見せない。 |
| P1 | search_descendants、markdown_export | 任意。未実装ならcapabilityを利用可能と告知せず、通常検索とCLI応答を使う。 |
| 展示後 | 大規模性能評価、旧形式の自動移行、その他の保留項目 | 本展示の合格条件から外す。採用には別の仕様判断が必要。 |

日常の9操作はmeta、search、detail、relation-detail、relations、history、save-draft、consult、apply。
init、backup、JSON export、restoreは、同じコアを運用するための必須の保守操作とする。
APIのHTTPメソッド・パスは契約の表記であり、初期の入口はJSON stdin/stdoutのCLIとする。診断ログはstderrへ出す。

参照実装はPython 3.11以上と標準ライブラリのsqlite3を推奨する。契約をPython固有のデータ表現へ依存させない。
初期は小規模データの正規化済み文字列走査を許す。NFKC＋casefold、空白区切り語のリテラル部分一致AND条件と安定した順位を守る。
日本語2文字を取りこぼすFTS置換は認めない。FTS、ベクトル検索、外部AI・Webサービスをコアの必須依存にしない。

### 11/4：記録・検索と最初の実利用

ID・個別版・snapshot_id・履歴・出所を持つ保存基盤を先に作る。原文と未確定情報を保存できるようにする。
save-draftも所定の構造検査・成功結果の冪等性・原子的保存を満たしてから実利用する。
日本語検索、Scope未分類の検索、ページングと打ち切りの表示を、小さな固定データで確かめる。
LLM Guideを実行するエージェントへ渡し、曖昧な語から検索をやり直せるかを観察する。
この日はdraft／proposedを明示して検索する。採択処理が未実装の間、DBへaccepted合意を直接注入して成立したことにしない。

### 11/5：照合・反映・履歴

照合したchange_setとbasisをapplyへ渡し、最後の前提検査と更新を短い同一トランザクションで行う。
変更前後のlifecycle、confirmation、直接Scope所属を見て、追加・撤回・置換・移動・確定関係の変化を検査する。
無関係なDB更新だけで全操作を拒否せず、監視外の未分類変更は非blockingの探索手掛かりとして返す。
成功済みidempotency_keyの同一入力はbasis再検査より先に成功結果を返す。異なる入力は拒否し、失敗はキーを消費しない。
対象・関係・来歴・履歴・成功結果の記録を原子的に保存する。LLM処理や人間の返答中に書き込みロックを持たない。
判断のtarget_refsは反映後の版を示し、consulted_basisは判断前の版を残す。実行者、指示の根拠、任意のprincipal_refsを追跡できるようにする。

### 11/6：実装観測・検査証拠とリハーサル

展示素材は通常ログ24時間→48時間の同一agreementの本文改訂とする。監査ログ90日＝2160時間は別合意で、説明用の架空設定である。
[retention.py](examples/demo_project/retention.py)と[test_retention.py](examples/demo_project/test_retention.py)を別々の通常artifactとして観測し、実際のバイト列のハッシュを記録する。
examples/demo_projectでpython -m unittest -vを実行し、アプリとテスト両artifactの参照版を持つ新しいevidence artifactを作る。
この素材はLATIS本体の実装ではない。[seed_consult.request.json](examples/seed_consult.request.json)等の要求例も通常のsave-draft／consult／apply経路で利用する。

evidenceは一回の観測の記録とし、対象版・方法・結果・観測日時・実行者を保持する。再実行や訂正は新規artifactと来歴で表す。
confirmed verified_byはpassedの証拠だけを対象とし、固定されたsubject_refsを自動的にbasisへ含める。
証拠が検査した版と現在版が違えば、古い結果をreconfirmするだけで最新検証へ付け替えない。新しい検査と証拠を必要とする。
別セッションにはGuide、DBへの接続方法、要求を渡し、前セッションの会話記憶なしで合意・判断・証拠を参照できるかを確認する。

### 11/7：起動と展示

新しい作業用DBを検証済みのformat_version=2の退避から復元し、metaでspec_version、rules_version、capabilitiesを確認する。
P1未対応なら通常の関係取得・追加検索と、CLI応答をLLMが説明する経路を使う。
外部LLMや通信が使えない場合は、保存済みの記録・再現ログを使う代替展示へ切り替え、その場の実行ではないと説明する。
初期化・復元・リセットは展示担当者の準備であり、通常の利用者にCLI操作を求める流れにはしない。

## 4. v0.2から維持する受け入れケース

A01〜A26を追跡し、A21の旧形式自動移行だけを展示後へ回す。その他は本版のP0で満たす。
構造的なfixtureの検証と、LLMが使った際の観察を分ける。エラーの詳細・判定順序はAPIを基準とする。

| ID | 状況 | 受け入れ基準 |
| --- | --- | --- |
| A01 | 未分類、別表現の重複、根拠が不足した記録から始める。 | 保存できる範囲を取り込み、検索と変更を開始できる。不明な状態や関係を推測で確定しない。 |
| A02 | 最初の検索で必要な合意に届かない。 | 見つかった用語・Scope・関係から追加探索できる。固定回数での終了を強制しない。 |
| A03 | 結果が件数制限で省略される。 | 省略と継続手段を示す。取得済み部分を全関連情報と説明しない。 |
| A04 | 同じ内容に見える記録が複数ある。 | 同一性を検討し、必要な範囲で整理できる。全体の重複解消を利用開始条件にしない。 |
| A05 | 新要求が既存合意と整合する、または変更方針まで指示済み。 | 指示で決まっている範囲は同じ許可を取り直さず、必要な検証を経て反映できる。 |
| A06 | 「ログを48時間」と依頼され、通常24時間・監査90日の別合意がある。 | 適用範囲が指示で決まらない場合だけ根拠付きで確認する。通常ログのみと決まれば、その合意を改訂する。 |
| A07 | 今回無関係の既存矛盾・未解決事項が残る。 | それだけで今回の反映を拒否しない。未解決事項は失わない。 |
| A08 | 自然文に「90日保存」とある。 | 明示されていない「90日以上」等へ変換しない。意味の比較はLLMの判断部分として扱う。 |
| A09 | 24時間から48時間への照合後、同じ対象agreementが別の更新で改訂される。 | 古い判断で48時間へ上書きしない。前提の変化と再取得先を返す。 |
| A10 | 監視Scopeでaccepted agreementの追加・撤回・所属移動が起きる。 | before／afterの状態・確認状態・所属を見て、範囲から出る変更も再照合の対象にする。意味的競合とは即断しない。 |
| A11 | 照合後、参照関係や検査対象のScope構造が変わる。 | 定義された検査範囲の変化を検出し、新しい構造で取得し直せる。 |
| A12 | 根拠となる前提が変わる。 | 再検討の契機と合意の効力を区別し、合意を自動失効させない。 |
| A13 | LLMが新しい競合関係を推定する。 | 推定と確定済み判断を区別し、確定済みとして黙って保存しない。 |
| A14 | 不正な参照や状態遷移を反映しようとする。 | 拒否し、本文・関係・来歴・履歴に部分更新を残さない。 |
| A15 | 失敗または成功応答の喪失後に再試行する。 | 成功済みキー＋同一入力は古くなったbasisでも元の成功を返し、版を増やさない。異入力は拒否し、失敗時はキーを消費しない。 |
| A16 | 同じ版・明示条件・rules_versionで構造的照合を繰り返す。 | 対象、診断、順序が再現される。LLMの文言一致とは区別する。 |
| A17 | 局所Scopeに上位と異なる記録やpriority値がある。 | 階層・局所性・数値で勝者を決めず、明示情報と必要な意味判断を使う。 |
| A18 | 合意への照会・変更が不要な作業を行う。 | 全作業共通の事前照会や承認を追加せず作業を進められる。 |
| A19 | 続きの取得前にDB版が変わる。 | CURSOR_STALEを返し、異なる版のページを黙って混在させない。再検索できる。 |
| A20 | 日本語の「保持」等の2文字、全半角・大小文字、記号で検索する。 | 原文を変えず、所定の正規化とリテラル部分一致AND条件・順位を満たす。 |
| A21 | 旧DBにconflicted等やis_inferred=falseの記録がある。 | 展示後の移行課題として保持する。展示版は旧形式を拒否し、推測で変換しない。後日も元データ・旧値・来歴を保全する。 |
| A22 | 照合後に草稿のconfirmed scoped_toを追加・終了する。 | その草稿・関係の版をbasisが参照していなければ、それだけで再照合を強制しない。明示参照していれば版変化を検査する。 |
| A23 | DBまたはJSONを退避・復元する。 | format_version=2と対応するDB形式でID・版・snapshot・来歴・証拠を保持する。旧形式や不正な参照は拒否し、部分的な復元を成功としない。 |
| A24 | LLMがCLIから9操作を呼ぶ。 | stdinのJSONに対しstdoutへ契約どおりの応答を返し、ログを混入させない。HTTPサーバーなしで利用できる。 |
| A25 | 古いバックアップから別履歴で同じgraph_revisionへ到達する。 | snapshot_idで古いbasisとcursorを検出し、連番一致だけで通さない。 |
| A26 | 明示参照した関係の追加根拠や再確認で維持する根拠が照合後に変わる。 | 追加根拠もbasisへ含め、端点の版だけで検査を済ませない。 |

## 5. 外部成果物・検査証拠の必須ケース

| ID | 状況 | 受け入れ基準 |
| --- | --- | --- |
| E01 | 外部アプリとテストを観測する。 | 別々のartifactにlocatorと実バイト列のcontent_hashを記録する。コアが取得・実行したと偽らない。 |
| E02 | 実際に許可されたテストを実行する。 | 新しいevidence artifactにアプリとテストの既存版、method、outcome、observed_at、actorを記録し、systemのcreated_atと区別する。 |
| E03 | passedの証拠を合意へ結ぶ。 | consult／applyでverified_byをconfirmedにでき、端点とevidence.subject_refsが自動的にbasisへ入り、履歴から検査対象版へ戻れる。 |
| E04 | failedまたはinconclusiveの結果、結果未記録のartifactを使う。 | 記録やcandidateの保存はできるが、その対象をverified_byのconfirmedにできない。失敗したという事実を消さない。 |
| E05 | 証拠が参照したアプリまたはテストの版だけが進む。 | verified_byのbasis_statusがchangedとなり、verification_basis_changedを返す。合意は自動失効させない。 |
| E06 | 古いpassed証拠を新しいコードへreconfirmしようとする。 | EVIDENCE_SUBJECT_CHANGEDで拒否する。basis_targetsの指定変更で古い実行結果を最新の検証へ付け替えられない。 |
| E07 | すでに版が進んだ対象の過去の検査結果を保存する。 | 参照版が実在すれば歴史的な証拠として保存できる。現在版に対するconfirmed検証としては受け入れない。 |
| E08 | 照合後に検査対象が変わる、または確認する同じbatchで対象を改訂する。 | 最終版と固定subject_refsを検査して拒否し、関係・履歴・冪等性記録の部分反映を残さない。 |
| E09 | 過去のevidence artifactのevidence／locator／content_hashを訂正する。 | 作成後の固定項目を更新できない。新しい証拠を作り、旧結果と来歴を保持する。 |
| E10 | 実ファイルだけが変わり、artifactは未更新。 | コアには検出できない限界を示す。LLMは現物を再観測・記録してから現在の実装を説明し、版変化後は再検査へ進む。 |
| E11 | 同じコードを再検査する、または証拠が一件もない合意を読む。 | 再検査は新しい観測として残す。検証関係がないことや診断0件を、検証成功と説明しない。 |
| E12 | 別のLLMセッションが履歴を読む。 | 判断時と反映後の版、実行者、任意のprincipal_refs／execution_context、検査対象と結果を区別して再利用する。自己申告を認証・同意の証明としない。 |

実行結果の自己申告だけで、現物との一致や未知の依存まで証明できるとは扱わない。
展示では実際のコマンド出力と記録された対象版を確認する。テキストを読んだレビューをテスト実行と呼ばない。

## 6. P1の受け入れと代替経路

| capability | 実装する場合の受け入れ基準 | 未対応時 |
| --- | --- | --- |
| search_descendants | 同一スナップショットでactive/confirmed containsを辿り、重複を除いたexpanded_scope_idsを返す。consultのwatchへ暗黙に広げない。 | capabilityを告知せず、通常のrelationsと追加searchを使う。要求を黙って無視しない。 |
| markdown_export | 指定範囲のtitle、ID、版、状態、外部参照、証拠を読める投影へ出す。範囲外の参照IDも見える。編集によるDB更新やMarkdownからのrestoreを行わない。 | capabilityを告知せず、CLI応答とLLMの説明を使う。JSONの退避機能は維持する。 |

P1を実装したと告知する場合は、その契約も検証する。間に合わなければ削るのはP1であり、P0の照合・原子性・証拠検査ではない。

## 7. 展示データと評価

展示は1,000ノード以下の小さな代表データで行う。これは展示で検証する規模であり、製品の対応上限ではない。
通常・監査ログの合意、未分類のメモ、重複候補、未解決事項、根拠、コード・テストのartifactを含める。
採択済みデータは通常のconsult／applyで作る。草稿や原文はsave-draftを使い、初期化時の裏口で採択を作らない。

操作の成功・失敗、対象版、変更結果、検索の不足・打ち切り、不要なユーザー確認を観察する。
中核の処理時間と、LLMの探索・推論・通信の時間を分ける。必要な判断を飛ばして速くなった結果は改善としない。
検索は日本語2文字、部分一致、表記揺れへの再検索、広いScopeと未分類を含むケースで確認する。
20万合意の性能は未測定・未達成であり、展示合格条件に含めない。展示後に本文長・関係数・Scope分布・履歴量を併記して評価する。

## 8. 11/6の凍結条件と11/7の引き渡し

- P0のAケース（A21を除く）とEケースの結果を残し、失敗・未実施を合格扱いにしない。
- 要求→探索→必要な折衝→合意改訂→実テスト→証拠→別セッションの再利用を通す。
- JSONの退避・復元を確かめ、動作確認した実装版・DB・Guide・デモ素材を組にして固定する。
- metaのspec_version=0.3-demo-draft、rules_version=core-0.3.0、対応capabilityと、format_version=2を確認する。
- 通信障害時の保存済み記録による代替手順を用意し、ライブ実行との区別をDemo Guideに従って説明する。

11/7は起動と既存フローの確認に留める。重大な不具合が残れば該当部分を動作済みと見せず、確認済み範囲と記録を提示する。

## 9. 展示後の課題

20万合意の測定、FTS等の索引、旧形式の自動移行（A21）を、実際の課題と評価結果から優先付けする。
独立したdrift操作、IAM／partyノード、ハッシュ由来の版ID、redaction、名前空間拡張、時間評価、hybrid、Scope epoch、Markdown importは別途検討する。
CSS的な優先・継承や自然文の全面形式化を、この予定表から自動的に採用することはない。
変更を採用する際はSpec・API・Operation・LLM Guideと受け入れケースを一緒に更新する。

| 同じ問いを語句・関係探索、推論検索、併用で調べる | 必要な合意・例外の発見、時間、追加検索・打診の回数を同じデータで比較する |
| 索引後に合意の改訂・撤回・追加がある | 古い本文の再取得と、新規候補の発見を別に検証する。古い索引だけで現在の全体を説明しない |
| Nodeの版を変えず、Scope所属・例外関係だけを変更する | 候補のNode RevisionRef一致だけで分類や適用関係も現在と判断しない |
| 未分類、多重Scope、言い換え、低頻度の重要な例外がある | 木の一つの枝に依存せず、別経路の検索と正本の関係取得で補えるか確認する |
| 索引を再構築する、または検索器・モデルを交換する | 合意のID・版・履歴・採択状態を変えずに交換できる。現行searchの一致条件とcursorを変えない |
| 推論検索の停止、低スコア、top-kの枝刈りがある | 既存の検索・更新経路を使える。consult/applyの構造検査を省略しない |
| 継続的にデータが増え、変更される | 検索時間に加え、構築・更新費用、更新遅れと取りこぼしを測る |

この評価の結果から検索方式を選ぶ。論文や他サービスの速度・精度を、未測定のLATISの達成値として使わない。
