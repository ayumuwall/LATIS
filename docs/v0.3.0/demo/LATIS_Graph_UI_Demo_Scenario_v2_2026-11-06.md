## 1. 15秒で何を伝えるか

**来場者への最初の説明：**

> 「AIと開発していると、前のセッションで何を決めたか忘れがちですよね。LATISはその合意と理由を保存します。AIに普通に仕様を頼むだけで、必要なときに過去の判断を調べ、変更が確定すると、このグラフが更新されます。」

**大きな画面のメッセージ:** `AIが忘れても、合意は残る。`

- MacBook：Claude CodeまたはCodexで通常の開発依頼。**人間はLATISのコマンドを入力しない。**
- 外部ディスプレイ：`LATIS / Agreement Explorer`。**Scopeの階層に合意と理由が整列**して表示され、**実際に確定した変更だけ**同じ位置で反転・差分表示される。
- 見せる核は「階層で現在の合意を読む → 追加 → 同じIDで改訂 → 以前の理由の再取得」。**ただノードが増えるデモにはしない。**

### 1.1 デザイン上の演出ルール（展示担当が守ること）

- **参考PDF p.2の整列された3列**を主役にする。線が多い「蜘蛛の巣グラフ」や暗いサイバー風へ戻さない。
- 色はモノトーンが基本。PDFのオレンジ`#FF4A1C`は**実applyの確定を短く示す任意の1色**だけ。新規＝緑・改訂＝琥珀、という多色の分類は採用しない。
- 初期画面は静的。待機中にノードが漂うこともない。**変化がないときは静かな道具**に見えるようにする。
- 新規は**行追加**、改訂は**同じ行の反転**。後者は変更前→変更後を読み上げる。変更前後の数値は実データに従う。
- PDFの大きな縦書きコピー、細かな円弧や装飾メーターは任意。読みやすい文字が優先。
- 正式表示名は`LATIS / Agreement Explorer`。旧仮称をデモのタイトルには使用しない。

## 2. デモ開始時の画面

### 展示データは架空のプロジェクト

通常ログと監査ログは別の合意。法令・実サービスの推奨値ではない。

| 対象 | 開始時 | 主実演の結果 |
|---|---|---|
| 通常ログの保持期間 | 24時間 | **48時間**に改訂 |
| 監査ログの保持期間 | 90日 | **変更しない** |
| 理由 | 障害調査・監査目的など | 変更理由が履歴から追える |
| 追加する仕様（展示用） | UTC記録の決定はない | 通常ログのタイムスタンプはUTCという合意を追加 |

開始画面は合意10〜30件程度に絞り、**Scopeの親子関係と通常ログ／監査ログの別々の行**を整列して示す。理由は、実際の`supports`等の記録があるときだけ隣の列へ。未確定は破線と「候補」ラベル。初期ロードでは過去の更新をアニメーションしない。

### 外部ディスプレイは3つのエリア

**中央:** Scope｜Agreement｜Contextの**整列した階層ブラウザ**。\
**右:** 選択中の合意、現在の本文、理由、改訂履歴・差分。\
**下:** `CHANGE LOG`（確定した追加・改訂の記録。実装できた範囲のみ）。

画面の右上には、`LIVE` / `REPLAY` / `RECORDED`のいずれかと、`graph_revision`を表示する。`LIVE`はローカルDBの現状態を実際に読んでいるときだけ使う。

## 3. メインシナリオ（通常2〜4分、LLMの応答時間で変動）

### ACT 0 — 目の前の合意を見せる

**操作:** MacBookでLLMのセッションを開き、外部画面では通常ログ24時間と監査ログ90日のノードを表示しておく。

**話すこと：**

> 「これが、過去に決まった仕様の状態です。文書の全文を毎回渡すのではなく、合意とその理由を個別に記録しています。変更するときは、これと照合します。」

**見せ方:** 最初の5〜10秒は、**ログ管理→通常ログ／監査ログ→各合意**を指でたどる。通常ログ24時間と監査ログ90日の違いを画面上で示す。関連する理由が右列にあることを短く示し、常時点滅・光の流れは使わない。

### ACT 1 — 合意が1行増える（追加の見せ場）

**LLMへ入力する自然言語の依頼（コピペ用）：**

> このデモプロジェクトで、通常ログのタイムスタンプをUTCで統一する仕様を追加してください。理由は、時差による障害調査の取り違えを防ぐためです。既存の決定と整合するか確認し、必要な内容を記録してください。

**演出の理想形：**

1. MacBook上のLLMが、LATISを自分で検索・照合する（来場者はCLIを打たない）。
2. 採択済みの新規AgreementがDBへ記録される。
3. 外部画面では**通常ログScopeの合意一覧に1行増え**、短い白黒反転と`NEW`で見せる。
4. 理由のRationaleが**実際に保存された場合のみ**、Context列に増える。確定関係は細い実線、候補は破線。
5. 右Inspectorに `NEW / タイムスタンプはUTC` と、実際に登録された理由・出所を表示。**単色アクセントを使う場合も確定後2〜3秒だけ**。

**話すこと：**

> 「いま、仕様が“文書の一行”として追加されたのではなく、合意の記録になりました。理由まで保存されていれば、次のAIも辿れます。」

**正確性:** LLMが単にコードやMarkdownへ書いた段階では、グラフに「確定」と表示しない。実際の`apply`成功と`graph_revision`増加を確認する。LLMが追加情報を必要とするなら普通に答える。

### ACT 2 — 同じ行が書き換わる（改訂の見せ場）

**LLMへ入力する自然言語の依頼（コピペ用）：**

> 障害調査のために、**通常ログ**の保持期間を24時間から48時間に変更してください。監査ログの90日という決定は維持してください。過去にこの保持期間にした理由も確認したうえで、変更の記録を残してください。

**見せ場：**

1. LLMが24時間の既存Agreementとその理由を取得し、改訂を照合する。
2. 同じAgreement IDに新しい改訂が適用される。
3. **通常ログの同じID・同じ行**を2回ほど短く反転させ、右Inspectorに**`24時間 → 48時間`**を大きく表示する。
4. 監査ログ90日の行は動かさず、「変更なし」と小さく明記する。
5. `history`を開けば、旧版・改訂理由へ戻れる。

**話すこと：**

> 「ここがポイントです。単に48時間という新しい文章を増やしたのではなく、以前の24時間という合意そのものを、理由を残して改訂しました。監査ログの別の決定は維持されています。」

**補足:** コード変更と実テストまで実施する場合、既存の`retention.py`／`test_retention.py`の**作業コピー**を使い、実行した証拠があれば追加表示する。時間が足りなければ検査画面の説明は省略してよい。テスト未実施のまま「検証済み」と表示しない。

### ACT 3 — セッションを替えても思い出せる（時間がある来場者向け）

**新しいCodexセッション、または新しいClaude Codeセッションへ入力：**

> このデモプロジェクトの通常ログと監査ログは、現在それぞれ何時間保持する決定ですか。通常ログについて、直近で変わった点と理由も調べて教えてください。

- **重要:** 前セッションの会話や答えを引き継がず、Guideと同一LATIS DBを使う。
- 期待する説明：通常ログ48時間、監査ログ90日（2160時間）、変更の記録・理由へたどれること。
- 取得できなかった事実は、無理に作らせず「未確認」とする。

**話すこと：**

> 「新しいAIに前の会話を覚えさせたわけではありません。同じ合意台帳を道具として読めるから、必要なときに以前の判断へ戻れるんです。」

## 4. 補助シナリオ：LATISが勝手に合意を決めない

主実演が安定した後にだけ見せる。これは**確認の必要なケースでLATISが立ち止まる**ことを示す補助シナリオ。

**LLMへの依頼：**

> ログの保持期間を48時間にしてください。

この依頼だけでは通常ログと監査ログのどちらか曖昧である。既存の24時間と90日の二つを参照し、対象を質問できることが価値になる。**この時点ではAgreement Explorerのaccepted行が変わらない**ことも見せられる。

**話すこと：**

> 「AIが全部勝手に決めるのではなく、過去の判断と食い違ったり対象が曖昧なときは、人間に必要なことだけ聞きます。」

時間が限られる場合は、これをメインに差し込まず、質問された場合の追加説明にとどめる。

## 5. 展示モードを3段階用意する

| モード | 使う条件 | 表示上の約束 |
|---|---|---|
| **LIVE** | Claude Code／Codexが実際の展示DBへ書き込み、ビューアがそのDBを読めている | `LIVE`。**`save-draft`を含む全revision増分を「確定」と見せず、実apply由来の確定のみ演出** |
| **REPLAY** | ネット不調やLLM応答待ちが長い。以前の**実commit**を順に表示 | `REPLAY`を常時表示。LLMによるその場の保存と説明しない |
| **RECORDED** | Viewer自体に障害。事前に実機で収録した映像を再生 | `RECORDED`と明示。録画時の状況を説明する |

**優先順位:** LIVE → REPLAY → RECORDED。観客に確実に価値を伝えるため、切替えに躊躇しない。ただし、モードを偽らない。

最悪、CoreやUIが止まったときの短い説明：

> 「こちらは、動作確認済みの記録を再生しています。実際の保存と改訂に対応した動きを映していて、ライブ実演ではありません。」

## 8. うまくいかなかったとき

| 現象 | 最初に確認すること | 対応 |
|---|---|---|
| LLMがLATISを使わない | Guideを読み、現在のDB・CLIの場所が渡っているか | 適切に接続し直す。来場者にLATISコマンドを打たせない |
| LLMが想定外の質問をする | 既存の合意・Scope・候補の曖昧さ | 必要なら答える。無理に承認済みとして採択しない |
| グラフが変わらない | CLIの`meta.graph_revision`とViewerの値 | 同一DBか、`apply`成功か、read-onlyサーバーの接続かを確認 |
| 行・ノードが増殖する | 既存合意のIDを保っているか | 改訂と新規作成の操作を区別。実DBを手で修正しない |
| 画面がガクつく | 全面再レイアウトしていないか | 装飾的なアニメーションを切り、Scopeの行位置と本文の視認性を優先 |
| ネット切断 | Core・Viewer自体はローカルで動くか | LIVE LLM実演は中止し、REPLAY／RECORDEDへ |
| DB接続エラー | ロック、絶対パス、プロセスを確認 | 直前の正しい画面を保持し、接続を復旧。それでも不可ならREPLAY |
| デモの結果が次回へ残る | resetのdestinationとDBパス | 新しいbaseline作業ディレクトリを作り、全クライアントを付け替える |
| モニターが映らない | 給電・映像対応ケーブル・拡張表示 | Mac内蔵画面を主表示に切替え、録画で説明する |

A.「モデルの会話履歴に依存せず、合意のID・版・理由・関係を別の台帳へ保持します。新しいセッションや別のAIが必要なときに検索できます。」

A.「採択済みの仕様と照合し、未解決の食い違いがあれば人間へ打診します。確定と提案を分けて管理します。」

**Q. これはただのグラフアプリ？**\
A.「グラフは展示のための窓です。正本はSQLiteの合意エンジンで、ID・改訂履歴・判断理由を管理しています。」

A.「20万件規模の評価は今後の課題です。今回は少数の実際の合意を使い、変更・照合・引き継ぎという使い方を検証しています。」

**Q. この画面は本当にリアルタイム？**\
A.「LIVEのときはローカルDBで確定した更新を定期取得しています。LLMの計算時間とは別に、確定した後の表示が変化します。REPLAYなら画面にそう表示しています。」

## 10. 3段階の成功基準

1. **最低成功:** LLMによる正式な`apply`の後に、Agreement Explorerの**対応するScopeの行**が追加・改訂される。合意と理由が読み取れ、監査ログ90日が保たれる。
2. **理想成功:** 追加と改訂を同じ来場者に見せ、**Scope階層・同じIDの更新・before/after・理由**を明確に示し、新セッションでも旧版の理由を取り出す。
3. **障害時成功:** 本物の記録によるREPLAY/RECORDEDで、何が採択されどこに履歴が残るかを正確に説明できる。

**合図になる一文:** 「人間はCLIを覚えない。AIも以前の会話を覚えなくていい。ただ、必要なときにLATISを道具として使う。」
