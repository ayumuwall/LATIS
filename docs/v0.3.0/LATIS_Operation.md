# LATIS Operation

- 版: `v0.3-demo-draft`
- 作成日: 2026-11-04（日本時間）
- 状態: 2026-11-07 の展示に向けた運用仕様。LATIS 本体の実装済み・検証済みを意味しない。
- 対象: 人間、コーディングエージェント、LATIS の役割と日常の運用。

## 1. 運用の目的

LATIS は、エージェントが必要に応じて使う外部の合意エンジンである。
人間は通常の対話で要求や判断を伝え、LATIS の専用操作を覚えなくてよい。
「LATIS で調べて」と毎回依頼されることを、利用の前提にしない。

目的は、過去の合意を探し直す負担と判断のやり直しを減らし、開発を進めやすくすることである。
一度の応答で完全なコンテキストを揃えることや、全仕様の読み直しを目標にしない。

## 2. 既合意と、この版での具体化

次は、この版が引き継ぐ設計上の合意である。

- 軽量な検索を繰り返し、ユーザーの問いとエージェント自身の問いを解く。
- Scope や関係が未整理でも、記録と検索を利用できる。
- 意味や適用を変える採択・更新は、既存合意と照合してから確定する。
- 既存合意との食い違いに未解決の判断が残る場合だけ、人間へ打診する。
- 原文と履歴を保持し、使用中に得た整理の結果を再利用する。
- LLM 向け使用文書は、継続して提供する製品の一部とする。

以下の操作と手順は、これらを実装へ落とすためのプロトタイプ案である。
物理テーブル、通信方式、検索方式の選択は、対応する Spec / API に従う。
CSS 的な局所優先や自動継承は未採用であり、この版では前提にしない。
本版では外部コードの観測と検証結果の記録を追加する。権限エンジン、優先規則エンジン、専用審査案件は導入しない。
未採択の旧 v0.3 改訂提案と、この `v0.3-demo-draft` の契約を混ぜない。

## 3. 役割分担

| 主体 | 責務 |
| --- | --- |
| 人間 | 目的・要求を伝え、既存の判断だけでは解けない食い違いについて判断する。 |
| エージェント | 問いを組み立て、検索を反復し、照合と変更反映を行う。必要な外部ファイルの観測・実テストも行う。 |
| LATIS | 記録済みの内容・版・状態・関係を返し、構造の照合と更新の整合性を担う。外部ファイルを自動取得しない。 |

エージェントが意味を推定した結果と、既に確定した合意・関係を混同しない。
人間の認可を記録から確認できる場合は、同じ認可を再び求めない。

## 4. 操作と API の対応

| 操作 | HTTP 契約 | 主な用途 |
| --- | --- | --- |
| `meta` | `GET /v1/meta` | 版、DB 識別子、利用可能な操作を確認する。 |
| `search` | `POST /v1/search` | 条件を変えながら候補を探す。 |
| `detail` | `GET /v1/nodes/{node_id}` | 選んだノードの本文、状態、来歴への参照を確認する。 |
| `relation-detail` | `GET /v1/relations/{relation_id}` | 関係の特定版や判断の前提を確認する。 |
| `relations` | `GET /v1/nodes/{node_id}/relations` | 必要な方向・種類の関係をたどる。 |
| `history` | `GET /v1/history/{target_type}/{target_id}` | ノード・関係の以前の版や判断理由を確かめる。 |
| `save-draft` | `POST /v1/actions/save-draft` | 原文、草稿、候補、新規 Scope を保存する。 |
| `consult` | `POST /v1/consultations/proposal-impact` | 変更内容を既存合意に照合する。 |
| `apply` | `POST /v1/actions/apply-proposal` | 前提を再検査して変更を確定する。 |

CLI は同じ操作名で JSON を標準入力から受け取り、同じ形式の応答を標準出力へ返す。
HTTP サーバーの起動や MCP 導入は初期利用の必須条件ではない。詳細は `LATIS_API.md` に従う。
`save-draft` は既存合意の効力を変えず、`apply` が確定した変更を反映する。その他は読み取り・照合である。
日常操作はこの 9 操作とする。検証関係は `detail`、`relations`、`relation-detail`、`consult` で調べ、別の `drift` 操作は設けない。
構造化されたエラーも標準出力の JSON 応答で返し、診断ログと進捗だけを標準エラーへ分ける。
追加の `search_descendants`、`markdown_export` は任意機能であり、`meta.capabilities` にある場合だけ利用する。

## 5. 利用を始める契機

エージェントは、過去の決定、理由、適用範囲、未解決事項が今回の作業に関係すると判断したときに利用する。
セッションの交代や、別エージェントへの引き継ぎでも、必要な判断を検索して確認する。
ただし、毎回すべての合意を取得する必要はない。

既に確認できている判断に沿う局所的なコード編集やテスト実行を、毎回の強制照合の対象にしない。
LATIS を呼び出すこと自体について、人間の承認を追加で求めない。

## 6. 通常の検索ループ

1. 今の作業で知りたいことを、一つまたは少数の問いにする。
2. `search` で候補を取得する。
3. 必要な候補だけ `detail` で読む。
4. 分からない点が残れば、語句を変える、範囲を広げる、関係や履歴を確認する。
5. 得られた内容から次の問いを作り、必要な間だけ繰り返す。
6. 今の作業を進められる情報が得られたら、作業へ戻る。

検索回数の固定上限や、一定の達成率を運用の目標にしない。
特定の回数で必ず終えることも、固定回数の問い合わせを消化することも求めない。
十分かどうかは、今の問いに答えられるか、残る不明点が今回の判断を変えるかで判断する。

## 7. Scope や関係が不足している場合

Scope が不明なら、語句や原文から検索を始める。既知の ID は詳細取得で参照し、出所は次の検索語の手掛かりにする。
検索で得た Scope は手掛かりとして使い、分類されていない項目がある可能性を残す。
関係がないことを、関連する合意が存在しない証拠にしない。
検索の `scope_ids` が空なら全体を探す。Scope を指定しつつ未分類も探す場合は `include_unscoped=true` とする。
子孫 Scope は暗黙に含まれないため、必要に応じて条件を変えて調べる。
`search_descendants` が使える場合は `include_descendants=true` で取得範囲を広げられる。
これは検索の補助であり、効力の継承ではない。`consult` の監視範囲も自動拡張しない。
未対応なら `UNSUPPORTED_FEATURE` を受けて直接 Scope の検索へ戻り、同じ結果が得られたと偽らない。

関係探索だけで不足する場合は、語句検索や別の入口で調べる。
探索が打ち切られた場合や未取得の範囲がある場合は、その限界を判断に反映する。
構造の不完全さだけを理由に、プロジェクト全体の作業を停止しない。
今回の意味判断に影響する不足と、後で整えられる不足を区別する。

## 8. 未整理の記録を残す

有用な要求、メモ、原文、判断の候補は、分類や関係が完成していなくても `save-draft` で残せる。
出所が分かる場合は付け、不明な出所を作らない。
元の文章を保持し、要約や抽出結果を元の文章そのものと取り違えない。

未整理の記録を保存しただけでは、採択済み合意にならない。
推定した関係や解釈も候補として扱い、確定済みの結果と区別する。
既定検索は `agreement` / `accepted` である。未整理の記録を探す場合は、対象の `kinds` と `draft` / `proposed` を明示する。
新規 Scope 登録と草稿の所属確定は API が許す範囲で行えるが、採択済み項目の改訂や所属変更は consult/apply を通す。

## 9. 合意を新設・変更するループ

1. 変更したい内容と、分かっている対象・理由をまとめる。
2. 必要に応じて検索を反復し、既存合意を確認する。
3. 採択・更新する内容を `consult` に渡し、既存合意との関係を照合する。
4. 既存の指示や認可で扱いが確定しているなら、その判断を再利用する。
5. 食い違いの扱いに未解決の選択が残るなら、必要な点だけ人間へ打診する。
6. 内容を変更した場合は変更後の内容を照合し、`apply` で確定する。

会話で新しい内容が決まったように見えても、既存合意との照合を省略して採択しない。
一方、既に解決済みの食い違いや認可を、LATIS の操作のためだけに問い直さない。

## 10. 人間への打診

LATIS への `consult` と、人間への打診は別の処理である。
照合の結果が得られるたびに、人間の操作を要求するものではない。

打診では、少なくとも次を短く示す。

- 今回の要求と、食い違う既存合意。
- 既存の判断だけでは決められない点。
- 維持、修正、例外化、置換など、今回必要な選択肢。

単なる取得漏れや検索語の不足は、まずエージェントが追加検索で解消する。
利用者にノード ID、関係の種類、API の呼び出し方法を選ばせる必要はない。

## 11. 採択済み合意の利用

確定済みの適用範囲や例外関係は、毎回人間へ確認せず利用する。
新しい候補が追加されたことだけで、採択済み合意の効力を変えない。
Scope の深さ、検索順位、更新日時だけを根拠に、どの合意が勝つかを新たに決めない。

関係や適用条件が自然文の解釈を必要とする場合は、その判断と構造的な事実を区別する。
未解決の食い違いが判明した場合は、通常の照合・打診・確定の流れへ戻る。

## 12. 使用中に構造を整える

検索や実装で重複、古い参照、誤った分類、関係の不足に気付いたら、必要な範囲から整理する。
整理を毎回の作業終了条件にせず、後で扱う候補として残してもよい。

| 整理の内容 | 扱い |
| --- | --- |
| 原文を保った索引の再作成など、意味・効力を変えない処理 | 既定の保守操作として実施できる。 |
| 不確かな分類、依存、競合、重複の推定 | 未確定の候補として記録する。 |
| 合意の統合、例外の確定、適用範囲の変更 | 意味や適用を変えるなら、照合してから確定する。 |

重複に見える文章を削除したり、原文を要約で置き換えたりして、出所と履歴を失わない。
繰り返し参照された rationale を義務へ変えたり、局所的な合意を広い範囲へ移して適用まで広げたりしない。
分割・抽出では元の intent と出所を辿れるようにする。新しい目的を追加する場合は、意味の変更として照合する。
見送った提案も、同じ検討を繰り返さないために必要なら理由とともに `rejected` へ移して保存できる。

## 13. 照合後に前提が変わった場合

エージェントは、照合結果とともに返された参照情報を確定時まで保持する。
LATIS は、確定に必要な参照版や検査範囲を再確認する。
前提が変わっていた場合は、必要な範囲を再照合し、古い結果を無条件に使わない。

改訂や関係の変化は、意味的な競合の証明ではない。
変化だけで `accepted` を自動的に失効させず、再検討の必要性を別に扱う。
再照合して判断が変わらなければ、同じ承認を再取得しない。

## 14. 保存するものと寿命

一時的な検索や打診のセッション全体を、必ず永続化する必要はない。
その場で続ける照合結果はクライアントが保持できる。
後日扱う記録・提案は必要に応じて保存し、採択・更新の判断は出所と履歴に残す。
採択時には変更後の対象版、判断理由、権限の根拠、照合に使った前提を残す。判断時の前提と変更後の版は異なる。
LATIS 上で検証の根拠として再利用するテストやレビューの実施結果は、§18 の新しい evidence artifact として記録する。

参照情報を失った場合は再取得・再照合する。
会話全文や全仕様の複製を、再照合の前提にしない。

## 15. 失敗と再試行

検索に失敗した場合と、検索が成功して候補がなかった場合を区別する。
LATIS に接続できないことを、既存合意が存在しないことと扱わない。
必要な情報を取得できない場合でも、影響を受けない調査や実装は進められる。

確定結果が不明な場合は、API が提供する確認・再試行の契約に従う。
応答を受け取れなかったことだけを理由に、別の新規変更として重複登録しない。
意味や適用の変更を確認できないまま、確定済みと説明しない。

## 16. LLM 向け使用文書

`LATIS_LLM_Guide.md` を、エージェントが参照できる場所へ導入することを推奨する。
使用文書は、問いの作り方、検索の反復、照合、記録、再試行を説明する。
最初の検索・利用評価からガイドを使い、機能実装が終わってから追加する手順にしない。
導入時は、エージェントが読むプロジェクト開始時の指示に、このガイドの場所とDBパス、利用できるCLIを記す。
ファイルを置くだけでエージェントが自動発見すると想定せず、既存の指示ファイルやエージェント設定から辿れるようにする。
エンジン内部の意味を特定のモデル専用の暗黙知に閉じ込めない。

文書は利用状況に応じて改訂し、API の版と整合させる。
エージェントが検索回数や確認の儀式を増やす方向へ、ガイドを肥大化させない。

開始時の指示へ組み込む文面の例（パスは導入先に合わせる）:

> このプロジェクトでは、過去の合意を調べ、合意を変更するためにLATISを使います。
> 使用文書は `docs/latis/LATIS_LLM_Guide.md`、DBは `.latis/latis.sqlite` です。
> CLI は `latis --db .latis/latis.sqlite <操作名>` の JSON 入出力を使います。開始時にガイドを読み、接続先の版・capabilities を確認してください。
> 過去の判断が関係するときは必要に応じて探索し、採択・意味変更前は照合してください。コードを検証済みと説明する前に、対象を観測して実際の検証結果を記録してください。
> 全コード編集への事前照会は要求しません。既存合意との未解決の食い違いだけをユーザーへ打診してください。

## 17. プロトタイプで確かめること

- 人間が専用操作を指定しなくても、必要な場面で利用されるか。
- 未整理の記録を見つけ、追加の問いで必要な合意に到達できるか。
- 不完全な構造でも作業が進み、分かった関係を後で再利用できるか。
- 食い違いを見落とさず、既存の認可を重複確認しないか。
- 照合後の変化を検出し、合意を勝手に失効させないか。
- 実コードの観測、失敗を含む実テスト、新しい証拠の記録、確認済み関係の更新を区別できるか。
- 別セッションのエージェントが会話の全文なしで判断・理由・確認した版を再利用できるか。
- 検索と照合の時間、追加確認、再説明、整理作業が開発の負担を減らすか。

検索の回数や一度の応答の情報量だけで成功を判断しない。
必要な情報へ到達する総時間と、誤解・手戻り・運用負担を合わせて評価する。
展示は小さな代表データで行う。20 万合意の性能評価は展示後の課題であり、未測定の速度や規模を達成済みと表示しない。

## 18. 外部コードと検証結果を結び付ける

### 18.1 記録する三つのもの

| 記録 | 内容 | 更新方法 |
| --- | --- | --- |
| agreement | 現在採択されている要求 | 意味・適用の変更は `consult` / `apply` |
| 通常の artifact | 観測したコード・テスト・入力等の所在と内容ハッシュ | `draft` のままなら `save-draft` で新しい観測版へ更新できる |
| evidence を持つ artifact | 一回のテスト・観測・レビューの対象版、方法、結果 | 実行や訂正ごとに新しい artifact を作る |

`locator` は呼出元が解釈する所在であり、Core は取得しない。相対 `file:` URI の基準となる作業ディレクトリを運用で明示する。
`content_hash` は呼出元が現物のバイト列から計算する。改行や文字の正規化をせず、記録の本文や推測から生成しない。
`implemented_by` は合意と実装の対応、`verified_by` は合意と確認結果の対応を表す。

### 18.2 通常の手順

合意と実装の検証関係を更新する場合に、次の手順を使う。すべての試行的なテスト実行を LATIS へ保存する要求ではない。

1. エージェントが対象のコード、テスト、今回の判断に関わる入力を実際に読む。所在・コミットや内容ハッシュを取得する。
2. 既存の通常 artifact を探し、観測内容が変わっていれば `save-draft` でその版を更新する。未登録なら作成する。応答にある実際の ID と版を使う。
3. 採択済みの合意に照らした、許可済みの検証を実行する。実行したコマンド、対象、結果を取得する。本文を読んだだけなら、その方法はレビューと記す。
4. 新しい evidence artifact を `save-draft` で作る。`subject_refs` に観測したコード・テスト等の既存版を、`method`、`outcome`、`observed_at`、`actor` に実際の記録を指定する。
5. `outcome=passed` の結果を使って `verified_by` を確定する change_set を `consult` へ渡す。必要なら旧関係の `retired` 化と、`implemented_by` の再確認も同じ変更へまとめる。
6. 未解決の意味判断がなければ、既存の認可を根拠に `apply` する。前提版の変化があれば必要箇所を取り直し、追加検証・再照合する。
7. 読み取りで、採択した合意版、コード・テストの版、検証結果、新旧の関係と履歴を確認する。

検証の対象となった合意版も `subject_refs` に含めると、何を満たしたと判断したかを結果から辿れる。
`subject_refs` は既存の履歴版を指す。コード更新と、その未生成の版を指す証拠の作成を無理に一つの change_set へ詰めない。
保存された artifact が `accepted` の場合、その更新は `consult` / `apply` で扱う。頻繁に観測する資源は `draft` に置く運用でよい。

### 18.3 旧証拠の扱いと失敗

新しい実行や、対象・方法・結果など観測内容の訂正は新しい証拠にする。旧証拠の `evidence`、`locator`、`content_hash` は作成後に変更できない。
補足本文・表示名・lifecycle は通常の版管理で更新できるが、そこで固定された観測結果を別の結果へ読み替えない。
失敗や判定不能も `failed` / `inconclusive` として残せるが、その結果への `verified_by` を confirmed にしない。
旧証拠の対象版が変わったとき、単に `reconfirm=true` や新しい `basis_targets` を指定して成功結果を新コードへ貼り替えない。
Core は証拠の固定された対象版も検査し、不一致なら `EVIDENCE_SUBJECT_CHANGED` を返す。最新の対象を検証して、新しい証拠へ結び直す。
実行中に対象が変わった可能性があれば、その結果を現在版の成功として使用せず、対象を確かめて検証し直す。

### 18.4 読み取り結果が示す範囲

`basis_status=current` は記録された参照版が一致することだけを示す。関係がないことや `untracked` は検証成功を意味しない。
`verification_basis_changed` は検証関係の参照版の変化であり、違反の証明でも合意の自動失効でもない。
外部ファイルだけが変わり artifact が未更新なら、Core はその変化を検知できない。「現在の実装を確認した」と述べる前に、エージェントが現物を観測する。
検証の主張は、記録した対象・入力・方法の範囲に限る。未知の依存関係まで網羅した保証にはしない。

## 19. 実行者と判断の出所

`actor` は操作の実行者、`principal_refs` は判断や依頼に関係した人・組織等の参照、`authority_ref` は apply の根拠となる指示・過去判断である。`principal_refs` から代表権や委任を推定しない。
`execution_context` は任意のモデル・実行情報であり、分からない値は作らず省略する。これらは既存の provenance に保存する。
自己申告の識別子を認証、連署、各当事者の同意証明として扱わない。既存認可の再利用は、対象と範囲が今回の変更に合うことを確認して行う。

## 20. 展示時の運用

展示の準備・初期化・復元は運営者の作業とし、通常の来場者には専用コマンドを要求しない。
[LATIS_Demo_Guide.md](LATIS_Demo_Guide.md) に従い、通常ログの合意変更、監査ログとの区別、実テスト、別セッションでの再利用を示す。
読み取り表示は通常の `detail` / `relations` / `history` の結果から作る。任意の Markdown 投影を使う場合も、出力版を明示し、現在の DB と同一とは無条件に扱わない。
