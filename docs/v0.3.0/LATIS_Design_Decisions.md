# LATIS Design Decisions

**版:** v0.3-demo-draft  
**更新日:** 2026-11-04（日本時間）  
**目的:** 11月7日展示へ向けた改訂の採否と、その理由を保持する。実装・実測の完了報告ではない。

## 1. この文書の使い方

仕様の意味は[LATIS_Spec.md](LATIS_Spec.md)、操作契約は[LATIS_API.md](LATIS_API.md)を実装する。本書は、どの提案をなぜ採り、どれをなぜ保留したかを説明する。保留欄の案を未記載の実装要件として補わない。

本版のフィールド名や優先度は、ユーザーの「11月7日の展示へ向けて仕様を整理・改訂する」という依頼を受けた設計上の選択である。過去の会話で個々のフィールド名まで承認済みだったとは扱わない。

本書は旧提案の全文を再掲せず、実装に必要な結論と設計理由を収める。元資料は検討履歴として参照できるが、実装LLMへ本版と同等の規範として渡す必要はない。

## 5. スリム化資料から引き継ぐこと

### 5.1 保存対象を決める基準

新しい項目を追加する際は、次を確認する。

1. 対象・内容版・判断を後から識別するために必要か。
2. 構造の検査、変更の再現、必要な前提の再利用に必要か。
3. 保存した事実から計算できる状態を、別の正本として二重管理しようとしていないか。
4. その場の検索説明や推定で足りるか、後で扱う候補として残す必要があるか。

全ての概念を永続フィールドへ増やさない。候補や草稿を保存できることは維持し、採択済み記録との区別を守る。

### 5.2 情報の具体的な配分

| 概念 | 本版の配分 |
| --- | --- |
| Decision record | 既存provenanceとdecisionを明確化。独立した必須審査オブジェクトを増設しない |
| Signal/警告 | 読取時のdiagnostics。後日扱うものはquestion/proposalとして必要時に保存 |
| Freshness | ノードの効力状態にしない。参照版から導出したbasis_statusを使う |
| 候補の関係 | candidateとして保存可能。confirmedの判断へ自動昇格しない |
| 文脈の十分性 | 保証値・confidenceとして保存しない。探索範囲、上限、次の問いを返す |
| 取得理由 | related_items.inclusion_reasons。永続のノード属性にしない |
| 外部対象との対応 | artifactのlocator/content_hashと出所。文書の段落を恒久同期しない |
| 使用モデル | 来歴内のexecution_context。合意本文の一律フィールドにしない |

### 5.3 自動的に復活させない案

- Clauseのfacet/applies_to/effect/override_policyを全合意の必須条件にしない。
- ReviewCaseの独立オブジェクトや固定の審査段階を毎回要求しない。
- candidateを保存禁止にしない。必要な途中結果を次のセッションへ持ち越せることを優先する。
- relationのlifecycle/confirmation/originを一つに潰さない。終了、確定状態、由来は異なる情報である。
- LATIS内部の専用LLMを必須にしない。呼出元LLMと同梱Guideが最初の利用主体である。
- 数値priorityを使わない代わりに、depends_on/governsから勝者を自動導出することもしない。

## 6. 意味を守りながら整理する

仕様改善提案の分類リファクターの原則は、次の受け入れ例へ引き継ぐ。

### 6.1 理由を義務へ変えない

「新しい情報を探す人が多い」というrationaleを、繰り返し参照されたという理由だけで「全検索は新しい順でなければならない」というagreementへ変換しない。新しい規範として採る場合は、変更内容と根拠を明示し、consult/applyを通す。

### 6.2 分類の変更で適用を広げない

「通常ログ」の合意を「全ログ」に整理し直しただけで、監査ログまで同じ保持期間へ変えない。検索用の所属と、本文が表す適用範囲を確認する。今後権限・優先規則を導入する場合は、所属変更がその評価を変えることも明示する。

### 6.3 分割・統合で意図を捏造しない

分割・統合では元ノード、原文、出所、意図への参照を残す。既存のrationaleを新しい義務の理由として自動的に流用しない。意味を変える場合は通常の合意変更として扱い、単なる整理と説明しない。

### 6.4 整理を完了条件にしない

今回に関係しない問題はquestionやcandidateとして残して進められる。分類レビューを毎回の採択や実装完了の必須gateにしない。機械が自然文のsemantic_delta=noneを一般的に証明できるとは表示しない。

## 7. 判断、観測、実装の関係

| 変化 | 解釈 |
| --- | --- |
| 外部ファイルが変わったが未観測 | コアには不明。現在の実装を説明する前に呼出元が観測する |
| 観測用artifactの版が変わった | 記録された根拠版と違えば再確認の契機。違反とは断定しない |
| 実テストがfailed/inconclusive | その結果を記録できる。confirmed verified_byの成功根拠には使わない |
| 新しい入力版で検査がpassed | 新しい結果artifactと、その対象版を根拠に確認関係を作る |
| 新しい合意を採択した | 合意の新しい版または明示的置換を記録。実装の追随は別の確認対象 |

実装が変わったことを理由に採択済み合意を自動無効化しない。現実に即した合意へ変える場合も、その選択と理由を照合・採択の経路へ戻す。

## 8. 10年を見据えて維持する境界

### 8.1 変えない意味

記録の同一性と内容版、合意と採択の出来事、実行者と判断・依頼に関係した主体、使用モデルと権限、分類と適用、検査対象と実行結果、候補と確定判断は区別する。保存方式や索引を替えても、過去の自己申告を別の保証へ読み替えない。

### 8.2 後段で設計する事項

- 複数当事者の意思表示、不同意・撤回と、その対象版。単一のprincipal一覧を全員の同意証明としない。
- 認証済みprincipalと委任の結合、読み取り範囲、採択済み本文やScope/関係の変更を含む保護操作。権限評価では変更前後を扱う。
- 有効期間と記録時刻。任意の過去日時を入力しただけで現在の認可を通せる設計にしない。
- 未知の語彙・追加データ・根拠版を失わない拡張プロファイル。未対応の意味を実行しない。
- 本文消去後の可用性・検証状態、複製先、保持範囲。ハッシュの一致だけで再読可能とは扱わない。
- 内容digest、署名、外部チェックポイント。内部の整合性、履歴の同一性、外部の信頼を別々に定義する。

これらを初期フィールドの予約で大量に先取りしない。展示で実際の利用を確認し、必要な運用と反例を得てから追加する。

## 9. 展示後へ持ち越す具体課題

1. 日本語の短い語、同義表現、Scopeの偏り、関係数、履歴量を含む20万合意の評価。
2. 同じLLM・情報・課題でMarkdownと検索を使う場合との比較。探索量、時間、再説明、不要な打診、維持作業を測る。
3. 旧形式の移行とMarkdown import。編集元版、出所、変更意図、冪等性を保持する。
4. 複数作業・複数リポジトリ・ブランチをまたぐ適用文脈。Git上の版参照とLATIS自体の分散マージを分ける。
5. 結果の観測主体・入力版・再利用条件を伴う検証の集約表示。独立drift APIは、この取得需要を確認して追加する。

P0の実装を開始するための未決事項として、これらを再投入しない。

## 10. DecisionRAG等を見据えた検索拡張（2026-11-04追記）

### 10.1 今回の判断と参照資料

将来の推論検索を組み合わせる境界を今明文化し、11月7日の必須実装は維持する。以下の設計判断はLATISへの適用上の判断であり、研究論文がLATISの整合性や性能を保証したものではない。

- ユーザー提示：[DecisionRAGの紹介と独自検証](https://qiita.com/kikuziro/items/cc82e6e4e4c215eac99f)。2026-11-01公開、11-02更新。
- 原論文：[Retriever-Free Retrieval: Navigating Documents with Decision Models](https://arxiv.org/abs/2610.35868)、2026-10-26提出。[本文](https://arxiv.org/html/2610.35868v1)の§3.4、§7、Appendix Fで、階層探索、枝刈りの限界、前処理と検索時費用の分離を確認した。
- 関連する実装：[PageIndex公式リポジトリ](https://github.com/VectifyAI/PageIndex)。木構造索引の生成とLLMによる探索を分ける例として参照する。

ここでいうDecisionは検索先の選択を含む。LATISの合意の採択とは別の操作である。特定製品・モデルや検索方式の存続を、基本オブジェクトの前提にしない。

### 10.2 今固定する境界

| 領域 | 保持する責務 |
| --- | --- |
| 正本 | 合意・原文・状態・版・明示関係・判断履歴を保持し、IDと版で取得できる |
| 派生索引 | 生成要約、埋め込み、クラスタ、探索用階層を管理する。再生成・削除・方式交換で正本の意味を変えない |
| 候補探索 | 任意の検索器が、元の記録へ戻せる候補を返す。順位・スコアだけで効力や採択を決めない |
| 判断と更新 | 正本の本文・状態・必要な関係を読み、既存のconsult/applyへ接続する |

Scopeは検索の手掛かりとして使えるが、索引の生成だけでcontains/scoped_toを自動確定しない。有用な分類を正本へ記録する場合は、既存の保存・照合・反映契約を使う。探索の都合による複数の木、重複した入口、未分類のままの記録を許す。索引は履歴の代わりではなく、履歴も現在の採択済み合意と区別して探索できるようにする。

### 10.3 将来の検索契約で保持すべき情報

次は後段の検索インターフェースで必要になる情報である。現版のNodeやsearchへ予約フィールドを追加する要求ではない。具体的なJSON、エラー、結果集合の保持期間は、その機能を採用するときに版付きで定める。

| 情報 | 目的 |
| --- | --- |
| 候補が参照する1件以上のNode RevisionRefと、必要なら元本文内の位置 | 要約・チャンクから原文の特定版へ戻る。候補IDを正本のIDと混同しない |
| 索引元のdatabase_id、snapshot_id、抽出範囲 | どのDBのどの記録を材料にしたかを識別。全体を索引化したとは暗黙に扱わない |
| 索引の版、構築方法・設定 | 同じ正本から異なる検索構造を作った場合を区別する |
| 検索方式・モデルと設定、問い、探索予算 | 順位や枝刈りを調べる手掛かり。記録だけで推論の厳密再現を保証しない |
| 検索結果を検証した正本の版・状態・関係 | 古い候補の分類・採択状態を現在の事実と取り違えない |
| 返した候補集合・順序と、取得理由・打ち切り | 結果の再表示、評価、必要な追加探索に使う。確率の高低を合意の優先順位へ変換しない |

検索結果をページングする場合は、その候補集合、索引版、検索条件に対する専用の契約を用意する。推論を毎ページやり直して同じ集合だと説明したり、現行searchのcursorを使い回したりしない。標準searchの決定論的な契約は保持する。

モデルの不応答、索引の未整備、正常な検索0件を区別して返す。これらを同じ成功・空配列にまとめない。推論検索のcapabilityと失敗時の扱いも、導入時の明示的な契約に含める。

毎回の全推論ログや全候補を、合意の正本へ永続化することは要求しない。評価や判断の説明に必要な探索記録は別に保存でき、実際に判断へ使った根拠版は既存の来歴へ残す。検索器の内部実装をノード・関係の基本語彙へ持ち込まない。

### 10.4 索引更新と取りこぼしを分けて扱う

候補を現在版で読み直すことは、採択状態や本文の変化への対策になる。ただし、その索引が知らない新しい合意、所属変更、後から追加された例外を発見する処理にはならない。Nodeの本文版が同じでも関係だけが変わり得るので、必要な関係も正本から取得する。

例えば索引の要約に旧版の「24時間」が残り、正本が「48時間」へ変わっていた場合、参照版だけ現在版へ差し替えてその要約を現在の本文として返さない。旧版の検索候補と現在取得した内容を分けるか、現在の原文から抜粋を作り直す。

将来の索引は、追加・改訂・撤回・置換・所属変更・関係変更を反映する。初期の実験は、一貫したJSON snapshotを材料に再構築できる。公開の差分購読APIや索引更新サービスを展示のP0へ追加しない。

更新の遅れや探索不足に対して、別の検索方式、Scopeを外した語句検索、未分類を含む取得へ戻れる経路を維持する。検索器の不調をLATISの保存・照合の停止条件にしない。全問い合わせで全記録の意味検査を強制せず、残る不足を区別しながら反復探索する。

低スコアや探索のtop-kを理由に、consult/applyのbasis/watchの検査を縮小しない。正本が返した明示的な例外・競合等も、検索順位だけで無関係と確定しない。

### 10.5 展示後の評価と拡張

同じLATISデータと問いを使い、既存の語句・関係探索、推論検索、併用を比較する。必要な合意と例外の発見、旧版・撤回済み合意の誤採用、未分類からの発見、索引更新の遅れ、追加質問と探索回数、処理時間、索引構築・更新を含む費用を観測する。既存のLLMが行う反復探索も比較対象に含める。

固定コーパスの問い合わせ時間だけを、継続更新される20万合意の運用性能へ読み替えない。将来、複数組織の閲覧制御を導入するときは、元文書だけでなく索引・要約・モデルへ渡す候補にも同じ閲覧範囲を適用する。

今回追加したのはSpec §8.4、APIの責務の説明、Guideと評価計画である。8種類のノード、9操作、spec_version=0.3-demo-draft、rules_version=core-0.3.0、format_version=2と既存のJSON形状は維持する。新しい検索APIやプラグイン実行基盤の実装は展示後に判断する。
