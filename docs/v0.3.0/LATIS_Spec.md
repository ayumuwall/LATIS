**Layered Agreement, Traceability & Intent System**  
**版:** v0.3-demo-draft.1
**更新日:** 2026-11-04（日本時間）  
**対象:** 2026-11-07の展示へ向けたプロトタイプ仕様。実装済み・性能達成済みという表示ではない。

**2026-11-04追記:** §8.4に推論検索の拡張境界を明記。展示のP0、操作数、保存形式、rules_versionは変更しない。

## 1. 目的

LATISは、合意・意図・根拠・未解決事項を保持し、LLMが必要と判断したときに過去の決定を探索し、変更を照合する道具である。人間は通常の言葉で依頼する。通常利用で人間がCLIを操作したり、毎回LATISの利用を指示したりすることは要求しない。

目指す成果は、過去の合意を探す時間、同じ判断・説明の繰り返し、合意を忘れた変更による手戻りの削減である。判断主体やLLMのセッションが変わっても、内容の版・根拠・変更理由へ戻れるようにする。

小さな問いに対して検索し、結果から生じた問いを続けて調べる。初回に完全な文脈を取得する必要はない。Scopeや関係が未整理でも利用を始め、必要になった箇所から修正する。「2〜3回」「95%」は利用姿勢の例であり、固定回数や達成率ではない。

11月7日の展示では、検索、未解決の選択の打診、採択・履歴、コードと検証結果の記録、別セッションでの再利用を一連の体験として確認する。

## 2. 本版の決定と文書の役割

### 2.1 維持する方針

| 方針 | 本版の契約 |
| --- | --- |
| 主な操作主体はLLM | 小さなJSON操作と、最初から同梱するLLM Guide |
| 自然文を保持 | 全合意のClause化、facet/effectへの変換を要求しない |
| 採択前に照合 | consult/applyを通し、既存の指示で決まらない選択だけを打診 |
| 未整理を許容 | 草稿・候補・未分類を保存でき、不完全さだけで全体を停止しない |
| 既存の授権を再利用 | 記録や再照合のためだけに同じ承認を取り直さない |
| 自動的な優先決定を保留 | Scopeの深さ、日時、priority、依存関係から勝者を導かない |
| 使いながら整理 | 意味・適用を変える整理は通常の合意変更として扱う |

v0.2のID、個別版、履歴、basis、監視範囲、再試行、原子的反映を維持する。その上に、外部artifactのlocator/content_hash、検証結果の記録、実装・検証関係、来歴内の主体申告と実行情報を加える。一般的な権限管理、優先規則、消去、内容アドレスID等は本版へ導入しない。

Claude Fableのv0.3提案と旧スリム化資料の採否は[設計判断](LATIS_Design_Decisions.md)に記録する。元資料の提案を、本版とは別の実装命令として適用しない。

## 3. コアの責務と情報の置き方

### 3.1 コアが保証すること

保存、語句検索、明示関係の取得、履歴、構造的な照合、版と監視範囲の再検査、原子的な更新を担う。保存された判断、構造的な事実、推定、未確認を区別する。

自然文の全競合の発見、探索範囲外に関連合意がないこと、自己申告された権限や実行結果の真実性は保証しない。意味の検討と次の探索は呼出元LLMが行い、未解決の選択は人間と相談する。

コアは外部URIを取得せず、テストやLLMを実行しない。外部資料を観測し、検査を実行して結果を登録する主体は呼出元である。

### 3.2 情報の配置

| 情報 | 配置 |
| --- | --- |
| 合意本文、確定関係、草稿、必要な候補、実行結果 | 版付きの保存記録 |
| 誰が何を根拠に採択・更新したか | provenance内の判断記録 |
| 現在のScope所属、参照版の一致、不一致診断 | 正本から導出するview/応答 |
| 取得理由、打ち切り、追加探索の手掛かり | API応答 |
| 一時的な全検索・全会話 | 必須の保存対象にしない |

候補を保存できることと、採択済みとして扱うことを分ける。専用Signal、ReviewCase、confidence、coverage、汎用flagsを初期の必須オブジェクトにはしない。必要な気付きや不採用理由は既存のquestion/proposalと来歴で残せる。

## 4. 基本オブジェクト

### 4.1 ノード

| kind | 意味 |
| --- | --- |
| agreement | 採択・変更・撤回の対象となる合意本文 |
| proposal | 後で再利用する変更案 |
| intent | 目的・意図 |
| rationale | 判断理由・根拠の説明 |
| question | 追跡する未解決事項 |
| scope | 探索や関連付けのための分類 |
| artifact | 原文、外部対象、観測・検証結果 |
| task | 作業の記録 |

ノードはid、revision_id、commit_revision、kind、title、body、lifecycle、created_at、updated_atを持つ。kindとidは作成後に変えない。title/bodyは自然文でよく、機械比較用Clauseへの変換を必須にしない。

本版はnullableのlocator、content_hash、evidenceを加える。非nullを許すのはartifactだけである。その他のノードではnullとし、自由な拡張フィールドやx:* kindは受け付けない。具体的な上限と検査はAPIに従う。

### 4.2 外部対象のartifact

locatorは呼出元が解釈するURI文字列、content_hashは呼出元が観測した外部バイト列のSHA-256である。相対ファイルの基準となる作業ディレクトリ、リポジトリ、ブランチ等の作業文脈は呼出元が識別し、出所やbodyへ残す。同じ相対パスを別のリポジトリと同一視しない。

外部対象を再観測してlocator/content_hashを更新すると、そのartifactの新しい版を作る。これだけで採択済みagreementの本文や効力を変えない。通常の観測用artifactはdraftのまま管理できるため、観測のたびに人間の採択を要求しない。

外部の実物が変わっても、観測結果がLATISへ登録されなければコアは知り得ない。content_hashが一致するという記録も、現物を今読み取ったことの代用ではない。

### 4.3 観測・検証結果のartifact

evidenceを持つartifactは、1回の検査・レビュー・観測の結果を表す。evidenceは次を持つ。

| フィールド | 意味 |
| --- | --- |
| subject_refs | 実際に確認した既存ノードのIDと版。1件以上 |
| method | 実行した検査・コマンド・レビュー観点 |
| outcome | passed / failed / inconclusive |
| observed_at | 呼出元が申告する実行・観測時刻 |
| actor | 検査・観測を行った実行主体の申告 |
| source_refs | ログ等の参照。省略時は空配列 |

created_atはLATISへの記録時刻であり、observed_atとは区別する。新しい実行や結果の訂正は新しいartifactにする。evidenceと、その結果自体のlocator/content_hashは作成後に書き換えない。補足本文・表示名・lifecycleの変更には通常の版と来歴を使う。

過去の版についての結果も記録できる。記録できることと、現在の合意・実装の検証根拠として確認できることは別である。subject_refsは実在する過去のノード版を指し、同じノードの複数の版を混在させない。

結果は呼出元の申告であり、コアが実行や本人性を証明するものではない。テストを実行していないレビューは、その方法をレビューとして記録する。未知の依存まで検証済みとは主張しない。

### 4.4 関係・版・判断

関係は独立したIDと版、端点、種類、状態、由来、qualifier、必要な根拠版を持つ。関係の種類や端点の訂正は、旧関係を終了して新しい関係を作る。ただし実行済みのsupersedesは終了させず、§7.3とAPIの置換の修復手順に従う。

Revisionはその時点の保存内容を保持する。Provenanceは変更対象の版、実行者、理由、出所を保持する。採択時には変更内容、decision、consulted_basis、validated_at_revisionも記録する。

decision/recordのprincipal_refsは、判断や依頼に関係した人・組織等を示す任意の参照である。actorは実行者、execution_contextは使用モデル等の任意の実行情報であり、これらから同意・委任・権限を推定しない。authority_refによる既存指示の参照を維持する。partyノード、全員連署、組織認証の検査は本版に含めない。

## 5. 同一性、版、正本

### 5.1 保存の単位

ノード、関係、過去版、来歴、commit、成功済み書き込みの冪等性記録を保存する。SQLiteのテーブル分割や検索索引は実装上の選択であり、正本の意味を変えない。

検索用の正規化文、要約、診断を原文の代わりに保存しない。派生表示は元のID・版へ戻れるようにする。

### 5.1.1 プロジェクト名

すべてのLATISデータベースは、metadataのproject_nameにプロジェクト名を保存しなければならない。プロジェクト名は前後の空白・制御文字を含まない1〜240文字の文字列とし、未指定・null・空文字・空白だけの名前を受理してはならない。初期化時に明示指定し、ディレクトリ名やScopeから推測して補ってはならない。

プロジェクト名はDBの表示名であり、database_idやオブジェクトIDの名前空間にはしない。同名の別DBも存在し得る。meta、SQLite backup、JSON export/restoreで保持し、Agreement Explorerのヘッダーは表示対象DBの名前を使う。長い名前はヘッダーの高さを増やさず省略し、全文を確認できるようにする。

この必須化に伴いspec_version=0.3-demo-draft.1、rules_version=core-0.3.1、SQLite user_version=3、JSON format_version=3とする。旧形式2は通常操作・restoreでは拒否する。名前を指定した明示的なmigrateだけが、検証済みの旧形式2から新しいDBへ移行できる。元DB、database_id、graph_revision、snapshot_id、オブジェクト・版・来歴・commit・成功済み応答を改変してはならない。過去の成功応答とbasisに記録された旧仕様・規則版も原記録として保持する。未成功の旧basisは再照合を要する。

プロジェクト名を後から変更する場合も、migrateで現行DBから名前を明示した新しいDBへ移送する。元DBを上書きせず、グラフの変更回数や過去の本文を変更しない。プロジェクト名の変更を合意の改訂と混同しない。

### 5.2 IDと版

- idは対象の同一性、revision_idは内容の版を表す。不透明な文字列として扱う。
- graph_revisionは変更トランザクションの連番、snapshot_idはそのcommitの不変の一意IDである。
- 同じ連番でも、バックアップ復元後に異なる変更で到達した履歴のsnapshot_idは異なる。
- 過去版は通常操作で変更しない。本文の消去や部分秘匿による例外は本版に設けない。
- これらは内部の版・参照契約であり、署名や外部改ざん検証の保証ではない。

revision_idを内容ハッシュへ切り替えない。artifact.content_hashと、LATIS内の記録のIDを混同しない。将来digestを追加する場合も、保存内容・派生情報・正規化方式を明示し、過去の解釈を変更しない。

#### 5.2.1 オブジェクトID

通常の利用でノードを参照するA-1形式の識別子を「オブジェクトID」と呼ぶ。従来の表示番号・表示IDと同じものである。各ノードには次のオブジェクトIDを付けなければならない。整数は1から始め、ゼロ埋めしない。2026-11-06のユーザー指示で採択した規約である。Core JSONのidは「内部ID」、revision_idは版の識別子として区別する。

| kind | 種類 | オブジェクトID |
| --- | --- | --- |
| agreement | 合意 | A-1、A-2、… |
| proposal | 提案 | P-1、P-2、… |
| intent | 意図 | I-1、I-2、… |
| rationale | 理由 | R-1、R-2、… |
| question | 問い | Q-1、Q-2、… |
| scope | 範囲 | S-1、S-2、… |
| artifact | 成果物 | AR-1、AR-2、… |
| task | タスク | T-1、T-2、… |

採番はDB内で種類ごとに独立させる。各ノードの作成版をcommit_revisionの昇順で並べ、同一commit内はノードidのUnicodeコードポイントによる辞書順を使う。草稿・提案段階から番号を付け、採択・改訂・所属変更・終了によって番号を変更してはならない。同じ連続した履歴内で終了した番号を再利用してはならない。

Scopeは番号の名前空間にしない。A-1はDB内の一つの合意を指し、S-1とS-2に属するA-1も同じオブジェクトである。所属の文脈を「S-1 / A-1」のように添えても、所属をオブジェクトの同一性へ組み込んではならない。

表示・検索・並べ替え・Scopeの折畳み・複数所属の参照行ごとに採番し直してはならない。同一ノードの過去版と現在版は同じ番号を使う。完全な履歴を保持したbackup/restoreでは番号も同じになる。REPLAYは対象時点に存在するノードの番号だけを表示する。

番号は保存された作成履歴から導出する表示情報とする。正本のidとrevision_id、Core APIの引数・保存形式を変更しない。画面の詳細では番号から元のidと版へ戻れるようにしなければならない。番号だけで別DBや巻戻し後の分岐を同一視してはならず、DB・snapshot・idで区別する。証拠を持つartifactもAR系列を使い、別のノード種類を作らない。

一覧、Scope見出し、詳細、文脈、関係の端点と変更履歴には同じ番号を使う。Scopeへのリンクを辿った場合は対応する見出しを展開・選択表示し、範囲オブジェクトの詳細と一覧上の位置を対応付けなければならない。

Agreement Explorerの一覧・Scope見出し・Inspector・Change Logでは、オブジェクトIDを共通の四角い枠で表示する。Inspector・Change Log内の枠は、一覧・Scope見出しより文字と余白を小さくする。Inspector内の所属・関係・証拠の参照と、Change Logから開く変更詳細でも同じ表現を使い、内部ID・版IDとは区別する。

#### 5.2.2 全動作に共通するオブジェクトID優先の原則

**通常の利用では基本的にオブジェクトIDを使わなければならない。オブジェクトIDで十分に対象を特定できる場面では、オブジェクトIDを使う。** これはシステムの透明性を確保するための全動作に共通する原則であり、画面だけに限定してはならない。人間とLLMの双方を対象に、入力・検索・参照・変更の説明、プロンプト、応答、通知、エラー、履歴、操作ログ、文書とエクスポートへ適用する。対象を説明する際は原則として「A-2 通常ログの保持期間」のようにオブジェクトIDと名称を使い、内部IDだけを提示して対象の理解を人に委ねてはならない。LLMの操作ログも、後から人が対象と動作を追える表示にしなければならない。

内部idは同一性の保持、revision_idは版の指定・照合に使う。正本の保存、正確なAPI呼出し、競合検査、DB・分岐間の照合、退避・復元、機械処理用の原記録など、これらのIDが必要な処理では保持・使用しなければならない。人向けのオブジェクトIDから元のid・版へ辿れるようにし、機械処理用の記録をオブジェクトIDへ不可逆に置き換えてはならない。読みやすくした操作ログと実際のコマンド・応答の原記録は区別する。

オブジェクトIDの解決にはDBと対象snapshotの文脈を使い、版指定が必要なら対象版も照合する。対応がない・古い・曖昧な場合に番号を推測したり、別DBの同じ番号を同一視したりしてはならない。その場合は名称と未確認の範囲を示し、必要な内部IDや版を補助情報として使う。関係には独自のオブジェクトID系列を追加せず、端点のオブジェクトID・関係種別・向きで十分ならそれらを使い、同じ端点間の複数関係の識別などに必要な場合は関係idを併記する。

現行Core API/CLIは内部id・revision_idによる入出力契約を維持する。オブジェクトIDの直接入力は未実装であり、現在は接続側が対応表で解決してCoreを呼ぶ。今後、入力にも同じ原則を適用するための共通解決機能をM6-13で扱う。未実装であることを、オブジェクトIDで十分な説明・ログへ内部IDを使い続ける理由にしてはならない。

### 5.3 Scope所属

scope_idsは独立した保存フィールドにしない。active/confirmedのscoped_toから導出する。Scope間の構造はactive/confirmedのcontainsで表す。containsに循環を許さない。

複数のScopeへ所属できる。所属や親子関係だけで、合意の強弱、効力の継承、採択権限を決めない。探索用の分類を、一般的な権限階層へ読み替えない。

## 6. 状態と診断

### 6.1 ノードのlifecycle

| 値 | 意味 |
| --- | --- |
| draft | 草稿・未整理の記録 |
| proposed | 提案・検討対象 |
| accepted | そのkindの用途として登録・採択した記録 |
| rejected | 採用しなかった草稿・提案 |
| superseded | 全体として置き換えられたagreement |
| retired | 撤回・終了した記録 |

現在の採択済み合意の基本集合はkind=agreementかつlifecycle=acceptedである。他のkindのacceptedまで規範的な合意になるわけではない。acceptedは、その台帳の文脈で採択した状態であり、全当事者の意思表示や実装の充足を自動的に証明しない。

questionのdraft/proposed/acceptedは未解決の問いとして扱い、解決・取り下げは理由を残してretiredへ移す。supersededはagreementに限る。終端状態からの復活は新しい記録と出所関係で表す。許可する遷移はAPIに従う。

### 6.2 関係の状態

lifecycle（active/retired）、confirmation（candidate/confirmed）、origin（agent/human/import/system/unknown）を分ける。agentやimport由来であることと、未確認であることを同一視しない。採択・確認済みになった記録まで、由来を理由に永久に候補として扱わない。

### 6.3 診断

診断はlifecycleを書き換えない。unscoped、basis_changed、recorded_conflict、candidate_conflict、partial_result、verification_basis_changed等を、対象IDと根拠付きで返す。

| evidence_kind | 意味 |
| --- | --- |
| structural_fact | 保存された構造・版から確認できる事実 |
| recorded_judgment | 特定の版について保存した判断 |
| agent_inference | 呼出元による推定 |
| unverified | 未登録・未確認である部分 |

参照版の変化は、意味的な違反や合意の失効ではない。合意と実装の食い違いが確認された場合は、実装の修正、または照合を経た合意変更を検討する。自動的に仕様を実装へ追従させない。

## 7. 関係と検証の意味

### 7.1 対応する種類

| 種類 | 向き・用途 |
| --- | --- |
| contains | Scope → 子Scope。分類構造 |
| scoped_to | 記録 → Scope。直接所属 |
| depends_on | 依存する記録 → 前提 |
| supports | 根拠 → 支える記録 |
| conflicts_with | agreement → agreement。記録された競合判断 |
| governs | 規範となる記録 → 対象。自動的な優先は計算しない |
| specializes | 具体化したagreement → 元agreement |
| exception_to | 例外agreement → 基本agreement |
| supersedes | 新agreement → 全体置換された旧agreement |
| originates_from | 派生した記録 → 元の記録 |
| implemented_by | agreement → 実装を指すartifact |
| verified_by | agreement → 確認結果を持つartifact |

各関係の型、重複、循環、変更可能なフィールドはAPIで検査する。priorityは互換性のための保存値としてのみ保持し、効力計算や表示の意味的な順位に使わない。

### 7.2 関係が確認した版

depends_on、supports、conflicts_with、governs、specializes、exception_to、implemented_by、verified_byは内容に依存する。confirmed化した際の両端ノード版と、明示された追加根拠をbasis_refsへ保存する。

参照版が現在版と違えばbasis_status=changedを返す。currentは記録された参照版が一致すること、untrackedは確認対象版の記録がないことを表す。内容に依存するcandidateも、確認対象版を持たなければuntrackedとなる。currentは意味的な完全性、現在の実物との一致、実装の正しさの証明ではない。

contains、scoped_to、originates_from、supersedesは同一性・所属・出所・実行済みの置換を扱う。本文改訂だけでその事実を失効させない。basis_status=not_applicableはこの定義済みの関係に使い、未知の種類を内容非依存と推定するために使わない。

### 7.3 例外と置換

exception_toをconfirmedにする場合は、例外条件をqualifierへ明示する。基本合意を暗黙に終了させない。supersedesの確定では、新しい側のagreementが変更後acceptedであることを確認し、旧agreementのacceptedからsupersededへの変更とconfirmed関係を同じトランザクションで反映する。新しい側には、すでにacceptedのagreementも使える。

部分変更は、明示した例外、同一合意の本文改訂、または合意の分割として扱う。局所性や新しさだけで置き換えない。実行済みsupersedesを履歴から取り消す操作は公開せず、訂正は新しい合意・出所・理由を残して行う。

### 7.4 verified_byの追加条件

confirmedのverified_byは、evidenceを持ちoutcome=passedのartifactを指す。evidence.subject_refsをbasis_refsへ自動的に含める。追加根拠欄を省略・変更しても、実際に観測した対象版を外してはならない。

確認・再確認時には、固定されたsubject_refsがchange_set反映後の対象ノード版と一致しなければならない。不一致はEVIDENCE_SUBJECT_CHANGEDとし、古い結果を新しいコードへ付け替えて確認済みにする経路を認めない。

対象のコード・テストが変わった場合は、それぞれのartifactを再観測し、必要な検査を実施し、新しい結果artifactを記録して新しいverified_byへ結ぶ。旧結果と過去の関係は履歴として残す。検査対象が同じで意味上の再確認だけを行う場合も、何を根拠にしたかを来歴へ残す。

implemented_by/verified_byの参照版が変わればverification_basis_changedを返す。これは採択を一律に拒否する理由にしない。検証関係が存在しないことも、検証済みを意味しない。

## 8. 探索

### 8.1 標準の操作

候補検索、詳細、関係、履歴を独立して使う。最初の語句で届かなければ、別表現、見つけたScope、出所、関係から再探索する。Scope未指定の全体検索と、Scope指定時に未分類を含める入口を維持する。

語句検索はNFKCとcasefoldで正規化した語の部分一致ANDであり、原文を変更しない。日本語2文字もこの契約を満たす。索引方式は固定しない。小規模展示データでは走査を許し、FTSやn-gram索引は同じ取得契約を満たす場合に利用する。

P1のinclude_descendantsは、明示したScopeの子孫を検索範囲へ展開する任意機能である。探索の便利機能であり、合意の継承ではない。未対応ならAPI所定のUNSUPPORTED_FEATUREを返す。consultのwatchを暗黙に広げない。

### 8.2 決定論性と部分取得

同じDB版・明示入力・rules_versionについて、対象集合、構造的診断、順序、ページング条件を再現する。LLMの意味解釈、次の問い、文章表現の一致は含めない。時刻を使う効力評価は本版にない。

1応答は同じスナップショットから返す。cursorは検索条件・DB識別子・commit・rules_versionに結び付け、DB更新後の続きはCURSOR_STALEにする。独立した検索を一つの過去スナップショットへ固定し続ける必要はない。

has_more=falseは指定条件の結果を読み終えたことだけを表す。構造が未整理であることや検索結果が空であることから、合意の不存在・完全な整合性を断定しない。同時に、それだけで作業を止めない。

### 8.3 取得理由

consultのrelated_itemsは、seed、explicit_relation_neighbor、same_scopeの取得理由を返す。これは構造上の取得理由であり、意味的に必須であるという保証ではない。件数上限、未取得範囲、next_queriesを使って追加取得へ進める。

### 8.4 推論検索を追加するときの境界

DecisionRAG型の階層選択、意味検索、再順位付け等を、呼出元や任意の検索モジュールとして組み合わせられる設計にする。以下は拡張時に守る境界であり、本版へ新しい操作・capability・必須モデルを追加するものではない。

1. 合意・原文・版・明示関係・判断履歴を正本とする。検索用の生成要約、埋め込み、クラスタ、探索用階層は作り直せる派生データに置く。索引の再構築やモデルの変更だけで、合意の版・採択状態を変えない。
2. 探索用階層はScopeとは独立して構成できる。正式なScopeを手掛かりに使うことはできるが、索引生成の副作用でcontains/scoped_toを自動確定しない。分類を正本へ記録する場合は既存の保存・照合・反映契約を使う。同じ合意を複数の検索経路から参照でき、未分類の記録も既存の検索で取得できることを保つ。
3. 推論検索の候補は元ノードのIDと参照版へ戻せるようにする。複数記録の要約は対応する複数の根拠を保持する。判断に使う本文・状態・必要な関係は正本から確認し、採択は既存のconsult/applyへ接続する。参照版だけ現在版へ書き換えて古い要約・抜粋を流用しない。検索順位やモデルのスコアは、効力・優先順位・確認済み関係を成立させない。
4. 索引の元になったDB・snapshotと、索引自体の版を区別する。候補のNode版が同じでも、scoped_toやexception_to等の関係が変わっている場合がある。現在の状態・Scope条件・必要な関係は正本で確認する。また、候補の現在版を読み直しても、古い索引から漏れた新規合意は発見できない。将来の差分更新、再構築、未分類を含む語句検索等へ戻れるようにする。毎回の全件取得や完全な意味網羅は要求しない。
5. 標準searchの一致条件・順序・cursorと、consult/applyの参照・監視検査を維持する。推論による順位・枝刈りを、この決定論的な結果へ無告知で混ぜない。推論検索の結果集合固定、ページング、再現記録は、導入時に別の契約として定める。
6. 推論検索の上位件数やスコアで、APIが定めるbasis/watchの検査対象を縮めない。検索候補の全件を判断済みの根拠として保存することも要求しない。根拠に使った版は既存のcontext.basis_refs等で明示する。

推論検索が利用できない場合も、ID指定、語句検索、関係取得、履歴と更新の経路を利用できるようにする。将来の検索応答に必要な情報と評価条件は[設計判断 §10](LATIS_Design_Decisions.md#10-decisionrag等を見据えた検索拡張2026-11-04追記)に整理する。

## 9. 記録、照合、判断

### 9.1 save-draft

原文、草稿、問い、候補関係、観測用artifact、結果artifactを、分類が完成する前に保存できる。新規Scopeのaccepted登録だけは探索構造の作成として許す。既存の採択済み記録や確定関係の意味を変える操作はconsult/applyを通す。細かな許可範囲はAPIに従う。

### 9.2 consult

具体的なchange_setと、実際に調べた起点・根拠を受け取り、構造、参照版、監視範囲、候補、未確認事項を返す。意味の競合が存在しないとは保証しない。

context.basis_refsや操作から必要な根拠を構築し、verified_byの固定subjectも既存の版・監視契約へ接続する。表示件数を小さくしたことを理由に、機械的に必要な検査対象を落とさない。全候補を読了済みとみなして巨大なread setを作る必要もない。

consultは通常永続化せず、書き込みを行わない。返されたnormalized_requestとbasisは、呼出元または薄いクライアントがそのままapplyへ渡す。

### 9.3 打診と授権

ユーザーの依頼から変更対象・置換・例外の扱いまで決まっている場合は、その指示をauthority_refに使う。新しい承認イベントを作るためだけの確認は不要である。

既存合意との食い違いを発見し、既存の指示や判断でも扱いが決まらなければ、その選択を人間へ提示する。未解決のままsemantic_review=readyと申告しない。LATISへ照合する前の会話で決まったように見えても、後で発見した食い違いは同じ規則で扱う。

### 9.4 apply

照合済みの要求とbasis、判断理由、権限の根拠、idempotency_keyを受け取る。更新対象版、必要な前提、監視範囲の変更、不変条件を反映直前に検査する。semantic_review=readyは呼出元の判断であり、コアによる全意味の証明ではない。

ノード、関係、版、来歴、commit、冪等性記録を同じ短いトランザクションで確定する。失敗時は一部だけ反映しない。LLM・人間・外部コマンドの応答待ちをトランザクション内へ置かない。

## 10. 変更検知と再試行

basisには対象・根拠の版、DBのsnapshot、rules_version、要求のダイジェスト、監視するノードとScopeを残す。クライアントが参照集合を削って必須検査を縮小できないよう、コアが基準時点の記録から再構築する。

検査は変更前後の両側を見る。監視Scopeから外れた採択済み合意、終了した関係、合意本文は不変でも変わったconfirmed関係や追加根拠も対象にする。監視と無関係な変更だけなら反映を続行できる。DB全体の連番が進んだという理由だけでは拒否しない。

未分類で構造上の接点を確定できない変更は、追加探索の手掛かりとして返す。未知の意味的関連まで捕捉するとは主張しない。再照合が必要でも、判断が変わらなければ人間の再承認を要求しない。

成功済みidempotency_keyと同じ入力の再送は、basisの鮮度を再検査する前に保存済み成功結果を返す。同じキーで異なる入力は拒否する。失敗時は成功キーを消費しない。APIの検査順序と全走査による判定を維持し、Scope epoch最適化は展示後に同値性を確認してから行う。

## 11. 文書、退避、互換性

原文や外部文書はartifactとして取り込める。文書の各段落と合意を恒久同期する仕組みを必須にしない。編集した文書を採択済み合意へ直接反映する経路も設けない。

P0では一貫したSQLiteバックアップとformat_version=3のJSON snapshotを扱う。ID、版、来歴、commit、成功済み再試行記録を保ったまま、新しい復元先へ検証して復元する。出力や既存DBを無断で上書きしない。

P1のMarkdown exportは読取専用の投影であり、title、ID、版、状態、出所等を含める。JSON snapshotの代わりに復元へ使わない。Markdown importと旧形式の自動migrationは本版に含めない。

未対応の保存形式は明示的に拒否し、知らない情報を捨てて復元成功にしない。v0.2の資料や退避は保持し、実データを移す場合は別途移行を検証する。新しい展示DBは架空のseedを通常操作から登録して作る。過去に採択・確認されたか不明なデータを確定情報へ推測変換しない。

## 13. 長期拡張の境界

今固定するのは、対象IDと内容版、合意と採択の出来事、主体と使用モデル、分類と権威、外部対象と観測結果、候補と確定判断の区別である。未実装の機能名を予約フィールドとして大量に保存しない。

将来、当事者や署名を加えても、現在のprincipal_refsやactorの自己申告を検証済みの同意へ読み替えない。未知の拡張関係を一律に内容非依存と見なさない。内容の消去を導入する際は、本文の取得可否、版の同一性、再検証可能性を別に定義する。

用途別の追加を可能にするため、schema/rules/exportの版と、未対応を明示する契約を維持する。基本オブジェクトを大きくする前に、既存のartifact、provenance、関係、応答で必要な意味を表せるか確認する。
