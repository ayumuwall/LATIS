# LATIS Operation

## 1. この文書の目的

この文書は、LATIS を日常の仕様検討・変更提案・外部インポート・エージェント利用の中で、どのように運用するかを定める。

LATIS の重要な使い方は、単に情報を保存することではない。**変更を書く前に、まず LATIS に打診すること** にある。

---

## 2. 基本方針

### 2.1 先に LATIS に打診する

人間のざっくりした指示や変更要求は、いきなり `spec.md` に確定仕様として書かない。

まず LATIS に照会し、次を確認する。

- どの agreement に関係するか
- どの scope に属するか
- 何と conflict するか
- 何を supersede または exception とみなすべきか
- どの question が未解決か
- なぜその仕様が存在しているか

### 2.2 文書化は照会の後で行う

文書は最初の真実ではなく、照会と判断の結果を表現する媒体とみなす。

### 2.3 人間が最終判断する

LATIS は構造的な照会結果を返すが、Go / Revise / Abort を決めるのは人間である。

---

## 3. 日常運用フロー

### 3.1 変更提案フロー

日常の変更は、次の順番で扱う。

1. 人間がざっくりした要求を出す
2. エージェントまたは UI が LATIS に打診する
3. LATIS が関連合意・衝突・影響・未解決事項を返す
4. 必要ならグラフ UI で局所関係を確認する
5. 人間が `Proceed` / `Revise` / `Abort` を決める
6. `Proceed` の場合、Proposal を LATIS に登録または更新する
7. 必要に応じて `spec.md` などの成果物を生成・更新する

### 3.2 外部インポートフロー

OpenSpec や既存文書など、外部から入る仕様も同じくまず LATIS に通す。

1. 外部 artifact を取り込む
2. proposal 候補に分解する
3. LATIS が既存 graph と照合する
4. `accepted` / `conflicted` / `incomplete` / `rejected` などの状態を与える
5. 人間が採用方針を決める
6. 必要に応じて文書や graph を更新する

外部から来たからといって、自動的に正本化してはならない。

---

## 4. `spec.md` の扱い

### 4.1 `spec.md` は proposal または rendering である

`spec.md` は重要である。しかしそれは、LATIS を経由せずに単独で最終的な効力を持つものではない。

### 4.2 `spec.md` に何でも書けることを前提にする

Markdown は自由に書ける。その自由さは有用だが、同時に矛盾・重複・上位原理との衝突を生みやすい。

そのため、運用上は次の前提を置く。

- 文書に書けることと、有効な agreement であることは別である
- 文書側の主張ではなく、LATIS 側の判定が状態を与える
- 文書には LATIS の判定結果を書き戻す

### 4.3 望ましいメタデータ

`spec.md` の各項目は、可能なら次のメタデータを持つ。

- stable ID
- scope
- status
- related agreement refs
- latis node id
- checked revision / checked at

### 4.4 ステータスの扱い

`accepted` などの状態は手入力ではなく、LATIS の結果として付与されるべきである。

---

## 5. Graph UI の役割

LATIS の打診結果は、可能なら視覚的にも確認できるべきである。

Graph UI は、巨大な全体図を見せるためではなく、**局所的な判断を助けるため** に使う。

打診時に最低限見たいもの:

- 対象 proposal
- conflict edge
- governs / depends_on / exception_to / supersedes の近傍
- 同 scope の question
- 関連 rationale

Graph UI は、文章の代替ではなく、**変更前の地形確認** のための面である。

---

## 6. エージェント運用方針

### 6.1 エージェントは LATIS に先に聞く

エージェントは、仕様提案・実装前調査・要約生成の前に、まず LATIS に問い合わせる。

### 6.2 エージェントは「通る文章」を作るだけではない

エージェントの役割は、単に既存の LATIS に迎合した文章を書くことではない。

エージェントは、要求を次のように正規化する補助者である。

- 新規 agreement
- 既存 agreement の具体化
- exception
- supersede
- question
- rationale 追加

つまり、エージェントは **proposal compiler** に近い。

### 6.3 エージェントは衝突を隠さない

本当に必要な変更が既存合意と衝突する場合、エージェントはそれを丸めてはいけない。

望ましい振る舞い:

- 何と衝突しているかを示す
- exception で済むか、supersede が必要かを示す
- rationale や scope の不足を示す

## 7. Skillpack の位置付け

### 7.1 なぜ Skillpack があるのか

初期段階では、LATIS への良い問い合わせ方はまだ暗黙知である。

そのため、エージェントには次のような作法が必要になる。

- ざっくり要求を change consultation に落とす
- scope summary を引く
- schema / constraint をまとめる
- 実装前の compact context を取る

この作法群を Skillpack と呼ぶ。

### 7.2 Skillpack は過渡的なものとみなす

理想形では、LATIS の問い合わせ面が十分に明示的・公共的になり、特定のエージェントだけが知る秘伝ノウハウは不要になる。

したがって運用上の立場は次の通りである。

- 今は Skillpack を使ってよい
- ただし Skillpack に本質を閉じ込めない
- いずれ LATIS 自体の問い合わせ面を公共化する

### 7.3 Skillpack の最小責務

初期プロトタイプで Skillpack が持つべき責務は限定する。

- 問い合わせの種別を選ぶ
- 応答を人間向けに要約する
- 必要に応じて follow-up query を組み立てる

データモデルの真実は LATIS 側に置く。

---

## 8. 人間と LATIS の役割分担

### 人間

- 何を変えたいかを出す
- 打診結果を見て判断する
- conflict を受け入れるか、設計変更するかを決める
- 最終的な採択責任を持つ

### LATIS

- 既存合意との関係を返す
- 影響と依存を返す
- scope の局所地形を返す
- 状態と履歴を保持する

### エージェント

- 要求を Proposal に正規化する
- LATIS への問い合わせを補助する
- 結果を整理して人間に返す
- 文書や成果物への反映を補助する

---

## 9. プロトタイプで優先すること

初期段階では、次を優先する。

1. ざっくり要求に対する change consultation
2. scope / agreement / question の局所グラフ表示
3. compact context bundle の返却
4. `spec.md` との stable ID ベースの対応
5. 文書への status 書き戻し

逆に、最初から大きくしすぎない。

- 大規模権限管理
- 高度な自動推論
- 全運用の完全自動化
- 巨大な統合 UI

---

## 10. 将来の展開

LATIS は、まず local-first または self-host 可能な形で有用であるべきである。

将来的に、クラウド型の仕様管理サービスとして提供される可能性はある。ただしそれは本質ではなく、**合意エンジンとして成立した後の提供形態の一つ** とみなす。

したがって運用の優先順位は次の通りである。

1. LATIS の中核体験を成立させる
2. 打診・照会・影響確認の価値を高める
3. その後に必要ならホスティング形態を広げる

---

## 11. 一文で言うと

LATIS の運用原則は次の一文に要約できる。

**変更は、書く前に LATIS に照会する。**

この原則を守ることで、仕様は単なる文章ではなく、既存合意との関係の中で扱われるようになる。
