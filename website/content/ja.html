01 / 仕様管理の課題

仕様が増えると、
決定の経緯を追いにくい。

AIコーディングでは、仕様を明文化することが役立ちます。一方、プロジェクトが大きくなると、複数の文書にまたがる仕様や決定の管理が難しくなります。

なぜその仕様になったのか。変更すると、どこに影響するのか。理由や依存関係が記録されていなければ、人間もエージェントも、文書や議論を探し直す必要があります。

Markdownは読み書きやレビューに適しています。ただ、文書単位で情報を探して渡す方法では、変更に関係する決定を特定しにくく、エージェントに無関係な情報まで渡しがちです。

LATISでは、個々の合意とその関係を、検索や影響確認の単位にします。

02 / 基本アイデア

合意の理由と、
仕様同士の関係を残す。

何が決まり、何が未解決で、どの決定に依存しているかを明示します。

合意・意図・根拠・未解決事項を、それぞれ識別できるデータとして保持します。「依存する」「競合する」などの関係を記録し、スコープで機能や領域ごとにまとめます。誰が、何を根拠に決め、どう変更したかも記録の対象です。

Markdownは引き続き、取り込み・書き出し・レビュー・表示に使います。合意の状態と関係はLATISの構造化モデルで管理し、Markdownだけを正本にはしません。

03 / 運用原則

書く前に、打診する。

変更要求をいきなり確定仕様として書かず、まず提案としてLATISに照会します。既存の合意との競合や依存関係を確認し、人間が採用するかどうかを決めます。

  1. 01 / INPUT

    変更要求

    意図を整理し、Proposal（提案）にする。

  2. 02 / CONSULT

    LATISに打診

    既存合意・競合・依存・スコープ・未解決事項を確認する。

  3. 03 / DECIDE

    人間が判断

    照会結果を確認し、採用・修正・見送りを決める。

  4. 04 / APPLY

    採択した変更

    採用した内容を合意に反映し、出所と変更履歴を保存する。

打診だけでは合意を変更しません。採択した変更だけを保存します。

打診セッション自体は原則として保存しません。採択後に合意を更新し、必要に応じて文書にも反映します。LATISは判断に必要な情報を返しますが、仕様の正しさや矛盾の解決を自動で決めるものではありません。

具体例：検索結果の並び順を変える +

提案：検索結果を新しい順に表示したい。

既存合意：既定は関連度順。ピン留め項目の優先順位も、まだ未解決。

判断：既存合意を置き換えるか、適用するスコープを絞るか、提案を修正するか。人間が判断した後に、採択した変更を反映します。

04 / エージェントに渡す情報

今のタスクに必要な
情報を渡す。

AIと連携でき、AIに依存しない。

仕様書を丸ごと渡す代わりに、タスクに関係する合意や制約をまとめます。

これをコンパクトなコンテキストバンドルとして返す設計です。決定の根拠、同じスコープの未解決事項、対象となる機能や領域の要約も含めます。

タスク → 関連する情報
  • 関連する合意と制約
  • 決定の根拠
  • 未解決事項
  • 対象の機能・領域の要約

人間も同じ合意や関係を確認できます。AIは検索や問い合わせの補助に使えても、合意のデータモデル自体はAIの生成結果に依存しません。

05 / 文書中心の管理との違い

管理の単位を、文書から合意へ。

文書中心

  1. 文書
  2. セクション
  3. テキストの差分
  4. エージェントが文書を読む

LATIS 設計構想

  1. 合意
  2. 型付きの関係
  3. 影響・根拠・スコープ
  4. 問い合わせに応じた文脈

LATISは、OpenSpecのような仕様主導ワークフローと、仕様を明確にして開発を進める考え方を共有しています。LATISではさらに、合意や関係を文書から独立したデータとして扱います。
