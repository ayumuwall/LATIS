Layered Agreement, Traceability & Intent System

An Agreement
Engine.

Manage agreements in software development.

LATIS is an Agreement Engine for recording what was agreed, why it was decided, and how it relates to other specifications. Changes are checked against existing agreements and dependencies, then applied with a recorded decision based on human instructions and authorization.

01 / The problem

More specifications.
Harder to trace decisions.

Written specifications help coding agents implement changes. As a project grows, those specifications branch and overlap across documents.

The reason for a decision may be buried in a discussion. A dependency may never have been recorded. Before changing a specification, people and agents have to reconstruct that context.

Markdown is useful for reading, writing, and review. But retrieving whole documents makes it hard to isolate relevant decisions, trace the impact of a change, and give agents only the context they need.

LATIS uses individual agreements and their relationships as the units for retrieval and impact analysis.

02 / The core idea

Record decisions,
reasons, and dependencies.

Make it explicit what is agreed, what remains open, and which decisions depend on each other.

Each agreement, intent, rationale, and question has a stable identity. Typed relations record dependencies and conflicts. Scopes group them by feature or concern, while provenance and revisions record where decisions came from and how they changed.

SQLite is the source of truth. Markdown is a read-only projection for review and display; editing it does not update the database. Restore uses complete JSON or SQLite snapshots. Markdown import is not implemented.

03 / The operating principle

Consult before you write.

Submit a change request as a proposal before writing it into the accepted specification. Consult LATIS for related agreements, conflicts, and dependencies. People and authorized LLMs make the decision, reusing clear existing instructions and asking only about unresolved judgments.

  1. 01 / INPUT

    Change request

    Shape the intent into a Proposal.

  2. 02 / CONSULT

    Consult LATIS

    Review existing agreements, conflicts, dependencies, scope, and open questions.

  3. 03 / DECIDE

    Authorized decision

    Reuse existing authorization and ask only about unresolved judgments.

  4. 04 / APPLY

    Accepted change

    Apply the accepted change and save its provenance and revision history.

Consulting does not change an agreement. Only accepted changes are saved.

Consult does not change the database. Apply rechecks referenced revisions and related changes, then saves the decision and updates atomically. Related candidates guide further exploration; they do not guarantee correctness or automatically resolve semantic conflicts.

A concrete example: changing normal-log retention +

Proposal: keep only normal logs for 48 hours to allow incident investigation.

Existing agreement: normal logs are kept for 24 hours and audit logs for 90 days. Their periods are decided independently.

Decision: reuse the explicit instruction and revise the existing normal-log agreement to 48 hours with the same ID. Preserve audit-log retention and record actual test results as new evidence.

04 / Context for coding agents

Give agents context
for the current task.

AI-compatible, not AI-dependent.

Return the agreements and constraints relevant to a task instead of entire specification documents.

The design calls for a compact context bundle that also includes the reasons behind those decisions, unresolved questions in the same scope, and a short summary of the relevant feature or concern.

TASK → RELEVANT CONTEXT
  • Agreements & constraints
  • Rationale
  • Open questions
  • Scope context

People can inspect the same agreements and relationships. AI can assist with retrieval and queries, but the core data model does not depend on AI-generated answers.

LATIS PROPOSED MODEL

  1. Agreements

LATIS shares the emphasis on explicit specifications found in workflows such as OpenSpec. Its storage model also treats agreements and relationships as structured data independent of documents.

06 / Current direction

Lightweight storage.
Inspectable data.

The v0.3.0 reference implementation

Storage
SQLite, typed nodes, typed directed relations
Retrieval
Deterministic substring search and explicit descendant Scope search
Traceability
Stable identity, provenance, revision history
Interfaces
JSON CLI, SQLite and JSON backup / restore, read-only Markdown projections

Core has no external runtime dependencies. FTS, vector search, and a graph UI are not implemented. Scope hierarchy does not imply agreement inheritance or priority. LLM acceptance uses the Claude CLI, and saved scripted results are distinguished from live runs.
